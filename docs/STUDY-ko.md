## 시작은 단순한 의심이었다

우리 팀 워크플로에는 이런 게 있다. 코드를 짜면 AI에게 리뷰시키고, 지적을 고치고, 다시
리뷰시킨다. 최대 3라운드까지 자동으로 돈다.

이 워크플로 전체가 하나의 가정 위에 서 있다. **리뷰를 더 하면 코드가 더 좋아진다.**

정말 그런가? 재봤다. 두 번 재야 했다. 첫 번째 실험이 틀렸기 때문이다.

그리고 재는 동안 내 결론이 **스무 번** 뒤집혔다. 방향은 항상 덜 극적인 쪽이었다. 마지막 두 번은 **내가 쓴 처방 자신이 반증된 것**이었다 — 7부다.

# 1부 — 실제 코드로 재보기

## 구성

실제 펌웨어 모듈 하나를 골랐다. `swing_capture.c`, 359줄. 센서 스레드가 쓰고 ML 스레드가 읽는
링버퍼라 동시성·상태 불변식·자원 한계가 다 들어 있다. 테스트 18개가 붙어 있고 19.5초에 돈다.

**격리가 핵심이다.** 매 리뷰는 완전히 새 프로세스로 띄우고, 코드는 프롬프트에 통째로 넣고,
리포지토리는 파일시스템 네임스페이스에서 아예 제거했다. 한 대화 안에서 10번 물으면 2회차부터는
1회차 답을 보고 있으니, 그건 수렴이 아니라 대화 기억이다.

### 여기서 첫 함정을 만났다

처음엔 CLI 플래그로 도구를 끄면 된다고 생각했다. **안 됐다.**

`codex` CLI에는 도구를 끄는 플래그가 없다. `-s read-only`는 셸 샌드박스 정책이고, 이름 그대로
**읽기는 허용**한다. 확인해보니:

```
bwrap 없이 codex 실행 →  /home/noel/spoton/TECH_SPEC.md 첫 줄을 그대로 읽어옴
```

플래그만 믿었으면 리뷰어가 우리 프로젝트 문서를 읽고 **코드가 아니라 우리 노트를 채점**했을
것이다. 통계는 멀쩡해 보였을 거고.

결국 `bwrap --unshare-all`로 네임스페이스를 만들고 **리포 경로를 아예 마운트하지 않는** 방식으로
갔다. 플래그를 믿는 대신 파일이 존재하지 않게 만든 것이다.

그리고 **"안 읽혔다"는 증명이 아니다.** 프로브가 고장나도 같은 답이 나온다. 그래서 모든 검증에
positive control을 붙였다 — 같은 실행 안에서 스크래치의 canary는 읽히고 리포는 안 읽혀야 통과.
둘 다 안 읽히면 격리 성공이 아니라 프로브 고장이다.

## 실험 1-A — 코드를 안 바꾸고 10번 리뷰

```
run:       01  02  03  04  05  06  07  08  09  10
findings:   6   6   5   7   5   7   9   5   4   7
```

**4건에서 9건. 2.25배 차이.**

61건의 지적을 같은 결함끼리 묶으니 **14개의 서로 다른 결함**이었다. 묶는 작업 자체도 검증했다.
순서를 바꿔 3번 돌렸더니 세 번 다 같은 분할이 나왔고(ARI 1.000), **다른 회사 모델에게 같은
61건을 묶게 했더니 역시 똑같은 14개**가 나왔다.

```
리뷰 1회 :  6.1 / 14  (44%)
      3회 : 10.0 / 14  (71%)
      5회 : 11.6 / 14  (83%)
      8회 : 13.2 / 14  (94%)
```

**14개 중 4개는 10번 중 딱 1번만 잡혔다.** 두 리뷰의 겹침(Jaccard)은 중앙값 0.36.

### 그런데 이 14개 중 4개는 오탐이었다 — 그리고 그게 가장 자주 발견된 것들이다

한참 뒤에 이 14개를 판정했다. 리뷰어는 `swing_capture.c` **한 파일만** 봤고, 나는 호출자
(`sensor.c`)와 초기화 경로(`main.c`)를 전부 읽었다. 거기서 갈렸다.

```
진짜 10 · 오탐 4          오탐률 29%

오탐 4건의 평균 발견빈도   6.8 / 10      (8, 7, 7, 5)
진짜 10건의 평균 발견빈도  3.4 / 10      (9, 7, 6, 3, 3, 2, 1, 1, 1, 1)
```

**발견빈도 상위 5개 중 4개가 오탐이다.** 넷 다 파일 밖 사실로 반증됐다.

| | 빈도 | 리뷰어 주장 | 실제 |
|---|---|---|---|
| D02 | 8/10 | 재초기화 시 큐에 남은 디스크립터가 오염된다 | `init()`은 부팅 시 **1회만** 호출된다 |
| D03 | 7/10 | `ring_total==0`에서 언더플로 | `ring_push`가 **항상 먼저** 돈다. 도달 불가 |
| D04 | 7/10 | `force_expire()`가 다른 스레드라 경쟁이 있다 | **같은 sensor_thread**다 |
| D07 | 5/10 | 호출 순서가 이러이러하면 오작동 | 실제 순서가 다르다 |

이유가 분명하다. **한 파일만 보고도 자신 있게 말할 수 있는 것이 곧 그 파일 밖에서
반증되는 것**이다. 스레딩 가정, 호출 순서 가정, 재초기화 가정은 파일 안에서는 전부
그럴듯하고 밖에서는 틀렸다.

> **"여러 리뷰어가 반복해서 지적하니 진짜겠지"가 이 데이터에서는 정확히 반대다.**

그래서 커버리지 곡선도 내려간다.

```
              14개 전체        진짜 10개만
리뷰 1회       44%              34%
      3회       71%              61%
      5회       83%              76%
```

**"리뷰 1회는 절반을 본다"가 아니라 "진짜 결함의 1/3을 본다"이다.**

*(판정자는 이 실험의 저자다. 다만 이 정정은 내 헤드라인을 나쁘게 만드는 방향이다.)*

## 실험 1-B — 고쳐가며 5번, 3번 반복

리뷰 → 수정 → 리뷰 → 수정. 고치는 AI는 테스트를 못 본다. 매 라운드 후 테스트를 몰래 돌린다.

```
        R1        R2        R3        R4        R5
루프1  6건/R4    6건/G    4건/R2    4건/G     1건/G
루프2  7건/R4   5건/R5   2건/R5   1건/R5    3건/R5
루프3  5건/R5   3건/R5   3건/R5   4건/R6    4건/R6
       (지적 수 / G=초록, Rn=빨강 n개)
```

15라운드 중 12개가 빨간 상태로 끝났다. 그리고 **네 번의 독립 실행이 정확히 같은 4개 테스트를
깼다.** 지적 건수도(4·5·6·7) 결과 코드 크기도(439~505줄) 다른데 파손 지점은 같았다.

여기까지 쓰고 "AI 수정이 버그를 만든다, 4/4 재현"으로 발표할 참이었다.

## 그런데 그게 버그가 아니었다

동료가 물었다. *"테스트가 뭘 테스트하는지 모르고 고쳐서 그런 건가? 정말 버그를 만드는
수정이라고 볼 수 있나?"*

확인해보니 아니었다.

AI가 추가한 것은 이 가드였다.

```c
 	if (session_id == 0 || rate_hz == 0) {
+		return;
+	}
+	if (ring_total == 0) {
+		/* 샘플이 하나도 없으면 armed_impact_gen 이 0xFFFFFFFF 로 언더플로한다.
+		 * 호출 순서(push 먼저)는 관례일 뿐이니 여기서 강제한다. */
 		return;
 	}
```

**판단도 주석도 정확하다.** 그런데 프로덕션에서 `ring_total == 0`으로 이 함수가 불릴 수 없다.
`sensor.c:1025`의 `ring_push`가 **무조건** 먼저 돌기 때문이다. 즉 이 가드는 **절대 발화하지
않는 no-op**이고, 깨진 4개는 `reset()` 후 push 없이 arming하는 **격리 단위 테스트**였다.
프로덕션이 도달하지 않는 상태를 고정해둔 것이다.

**코드는 안 깨졌다. 테스트만 깨졌다.**

7개 깨진 테스트를 성격별로 나눠 다시 세니 실제 파이프라인 파손은 15라운드 중 **10**이었다.
12가 아니라.

### 내가 저지른 진짜 실수

**오라클을 도입해 놓고 그 오라클이 무엇을 보증하는지 검증하지 않았다.**

실험 내내 클러스터러는 3번 돌려 ARI로 검증하고, 교차모델로 한 번 더 검증하고, 우연 수준을
계산하고, 뮤테이션으로 테스트를 검증했다. **그런데 정작 최종 판정 기준인 테스트 스위트는 한 번도
검증하지 않았다.** "빨개졌다"를 "버그가 생겼다"로 자동 번역했다.

지적받지 않았으면 그대로 발표했을 것이다.

# 2부 — 계약을 먼저 만들고 다시 재기

## 구멍을 구조적으로 막기

1부가 무너진 이유는 오라클이 **반박 가능**했기 때문이다. 어떤 실패에 대해서도 *"그 테스트가 과잉
명세였다"*는 빠져나갈 구멍이 열려 있었다.

그래서 순서를 뒤집었다.

```
1. SPEC 확정 (19개 인수 조건)     ← 사람 검토 후 동결
2. 인수 테스트 작성               ← 스펙만 보고, 구현 존재 전에
3. 구현                          ← 스펙만 보고, 테스트 못 봄
4. 인수 테스트 실행 = 준수율
5. review → fix 반복             ← 리뷰어·수정자 모두 테스트 못 봄
6. 매 라운드 준수율 재측정
```

구현자·리뷰어·수정자 **모두 계약을 산문으로 이미 받았다.** 테스트는 그 계약만 검사한다.
따라서 실패 = **자기가 받은 계약을 못 지킨 것**이다.

대상은 재시도 정책(지수 백오프 + full jitter + 서킷 브레이커), Python 156줄.

### 이번엔 검증부터 했다

**계약이 모호한가?** 다른 모델에게 스펙만 주고 구현시켜 봤다.

```
참조 구현 (내가 씀)   23/23  첫 시도
codex 독립 구현       23/23  첫 시도
claude 구현           23/23  첫 시도
```

세 개의 독립적 해석이 수렴했고, 테스트는 한 줄도 수정하지 않았다.

**오라클이 뭘 보증하는가?**

```
정답 구현                   19/19  ✅
AC-19 검증만 고의로 제거      18/19,  AC-19 정확히 지목  ✅
import 불가능한 쓰레기         0/19,  importable=False  ✅
```

이것이 1부에 없었던 것이다.

## 실험 2 — 정답 코드를 리뷰시키면

시작점이 **검증된 19/19 구현**이다. 리뷰가 개선할 여지가 없다. 그래서 질문이 바뀐다.

> 계약을 100% 만족하는 코드를, 그 계약을 손에 쥔 리뷰어에게 보여주면 무엇을 말하는가?
> 그 말을 들으면 어떻게 되는가?

프롬프트는 두 종류를 준비했다. 차이는 **범위 지시 한 곳뿐**이다(diff로 확인).

- **팔 A**: `"Review this code."` — 사람들이 실제로 타이핑하는 것
- **팔 B**: design → functionality → complexity → robustness → naming → style — 코드리뷰의
  교과서적 정의(구글 가이드 순서)

## 결과 1 — 리뷰어는 정답 코드에도 말한다

```
              지적 수 (같은 코드 7회 반복)          중앙값
claude bare    5, 5, 6, 8, 7, 8, 6                  6
claude struct  11, 11, 12, 11, 12, 12, 11          12
```

**14번 전부 지적이 나왔다. 0건은 한 번도 없다.**

그리고 대부분 **정당한 지적**이었다. 억지가 아니다.

```
major  state 읽기만 해도 open→half_open 전이가 일어남 (부수효과)
minor  except BaseException 이 KeyboardInterrupt 까지 회로 실패로 셈
minor  백오프 지수가 saturate 안 하고 오버플로
```

19개 AC는 코드의 동작 표면 전체를 덮지 못한다. **계약이 안 덮는 영역에서 진짜 문제를 찾는
것**이고, 실무에서 스펙은 절대 전부를 덮지 않으니 이게 현실적이다.

## 결과 2 — 그런데 codex는 침묵했다

여기서 동료가 또 물었다. *"코덱스로도 하는 건가?"*

아니었다. 전부 claude였다. 붙여봤다.

```
같은 코드, 같은 프롬프트, 7회 반복

claude bare   5, 5, 6, 8, 7, 8, 6      중앙값 6,  0건 없음
codex  bare   1, 1, 1, 1, 0, 1, 1      중앙값 1,  0건 있음
```

**codex는 "보고할 것 없음"을 냈다.**

그리고 루프를 돌리자 결정적인 그림이 나왔다.

```
codex  bare:        1 → 1 → 0 → 0 → 0        3라운드에 완전 침묵
codex  structured:  6 → 3 → 2 → 1 → 1        가파르게 감소, 0 에는 안 닿음
claude bare:        5 → 6 → 7 → 6 → 7        감소 없음
       (루프 2)     7 → 7 → 6 → 6 → 5
       (루프 3)     6 → 7 → 9 → 5 → 8
claude structured: 12 → 11 → 10 → 11 → 9     감소 없음
```

**codex는 두 팔 모두 감소했고 claude는 두 팔 모두 감소하지 않았다.** 그리고 **넷 다 준수율은
19/19를 유지했다.** claude가 계속 말한 그 6~12건은 코드가 나빠서가 아니다.

### 그런데 "멈췄다"가 "다 봤다"는 아니다

처음엔 codex bare의 침묵을 우월한 것처럼 읽었다. 두 팔의 지적 **내용**을 나란히 놓으니 그
해석이 위험했다.

codex bare가 5라운드 동안 말한 것은 딱 둘이다.

```
R1  백오프가 상한 적용 전에 오버플로
R2  cooldown 이 0 이면 open 상태가 가려짐
```

codex structured는 그중 하나를 똑같이 잡으면서, bare가 **한 번도 언급하지 않은 계열**을
추가로 찾았다.

```
major  시계 실패가 부분 트립 상태를 남김
major  시계 실패가 함수의 예외를 가림
major  트립 실패가 조용히 감춰지고 stale cooldown 을 남김
major  non-retryable BaseException 이 half-open 을 wedge 시킴
minor  프로세스 제어 예외(KeyboardInterrupt 등)가 브레이커를 변형
```

**bare의 침묵은 다 봤다는 신호가 아니라 덜 봤다는 신호일 수 있다.** 같은 코드에서 structured는
계속 실재하는 실패 모드를 찾고 있었다.

*(다만 이 지적들이 진짜인지는 판정하지 않았다. 내가 말할 수 있는 것은 "bare가 언급조차 안 한
영역"까지다.)*

### 같은 자리에 도달하는 비용이 크게 다르다

```
claude bare:        97건 말함 → 72건 반영 → 코드 +50%  → 19/19
claude structured: 147건 말함 → 117건 반영 → 코드 +24% → 19/19
codex  bare:         2건 말함 →  2건 반영 → 코드  +4%  → 19/19
codex  structured:  13건 말함 → 11건 반영 → 코드 -12%  → 19/19
```

**codex structured만 코드를 줄이면서 같은 자리에 도달했다.** 156 → 137줄. claude는 두 팔 다
붙이기만 했다.

*(codex는 각 팔 1루프, claude는 각 팔 3루프다. codex 쪽 표본이 훨씬 얇다.)*

## 결과 3 — 한 번 돌리면 절반만 본다

이게 세 번의 다른 조건에서 반복된 유일한 숫자다.

```
1부, C 펌웨어, 좁은 프롬프트         44%   (오탐 제외하면 34%)
2부, Python, bare 프롬프트          52%
2부, Python, 구조화 프롬프트         55%
```

대상도 언어도 프롬프트도 다른데 같은 자리다. 리뷰 한 번은 **그 리뷰어가 볼 수 있는 것의 절반**을
본다.

## 결과 4 — 개수가 일정한 것은 내용이 같은 것이 아니다

claude 구조화 팔은 11~12건으로 거의 완벽하게 일정했다. "일관성이 생겼다"고 읽고 싶어진다.

```
지적 수:    11, 11, 12, 11, 12, 12, 11     ← 거의 완벽
내용 겹침:  Jaccard 0.57                    ← 절반 조금 넘게만 겹침
```

**매번 11건씩 나오되 그중 40%는 다른 것이다.**

## 결과 5 — 계약을 쥔 수정자는 1/4을 거절한다

1부에서 수정자는 지적을 **전부** 받아들였다. 거부 0건. 코드에 관해서만 알고 있었으니 거절할
근거가 없었다.

2부에서는 계약을 같이 줬다.

```
claude bare        97건 → 72채택 / 25거부 (26%)
claude structured 147건 → 117채택 / 30거부 (20%)
```

거부 사유가 계약 조항을 직접 인용한다.

> *"AC-19는 생성 시점에 `ValueError`를 던져야 할 설정을 정확히 열거하고 `retryable`의 형태는
> 거기 없다. 검증을 추가하면 문서화된 계약을 조인다."*

> *"AC-13은 시험 호출 시점에 관찰되는 state를 못박은 것이고, 지연 보고로 바꾸면 AC-10과 직접
> 충돌한다."*

**리뷰어는 계속 계약 밖으로 나가자고 하고, 수정자는 계속 막는다.**

40라운드 동안 계약이 한 번도 안 깨졌다.

## 결과 6 — 리뷰가 없으면 아무것도 안 바뀐다

*"그건 리뷰 효과가 아니라 그냥 수정 기회를 더 준 효과 아니냐"*는 반박을 막으려고 대조군을 뒀다.
지적 없이 "스펙 준수도를 높여라"만 주고 같은 횟수를 돌렸다.

**모델은 코드를 한 줄도 안 바꿨다.**

> *"모든 인수 조건을 모듈과 대조해 추적했고 위반을 찾지 못했다. 그래서 파일을 바이트 단위로
> 그대로 반환한다."*

리뷰가 있으면 고치고, 없으면 안 고친다. **둘 다 19/19다.**

# 3부 — 1부와 2부는 왜 정반대였나

1부는 회귀가 4/4로 재현됐고 2부는 40라운드 무손상이었다. 원인 후보가 셋 있었다.

1. 수정자가 **계약**을 쥐었는가 (2부에만 있었다)
2. **외부 호출자**가 존재하는가 (1부에서 깨진 건 전부 모듈 바깥 계약이었다)
3. **C 펌웨어냐 Python 소형 모듈이냐**

1번은 유일하게 실행 가능한 처방이라 먼저 검정했다. 2×2를 돌렸다.

```
                     계약 있음         계약 없음
C 펌웨어 (1부)        ← 신규 8콜        4/4 파손 (기존)
Python  (2부)        0/40 (기존)       ← 신규 10콜
```

**1부 쪽**: 라운드 1을 4번 재실행하되 수정자에게 `swing_capture.h`(공개 헤더 = 실제 계약)를 준다.
리뷰어는 1부와 완전히 동일.
**2부 쪽**: 수정자에게서만 스펙을 뺀다. 리뷰어는 2부와 동일하게 스펙을 받는다.

## 결과 — 계약 가설은 기각됐다

```
                     계약 있음        계약 없음
C 펌웨어              3/4 파손         4/4 파손      ← 매번 같은 4개
Python               0/40 손상        0/5 손상
```

4/4 → 3/4. Fisher 정확검정 **p = 1.0**. 개선이 없다.

**행(대상) 효과는 압도적이고 열(계약) 효과는 0이다.** "수정자에게 계약을 주면 회귀가 막힌다"는
내가 1순위 처방으로 쓰려던 문장이었고, 데이터가 기각했다.

## 그런데 여기서 진짜 설명이 나온다

C 셀에서 깨진 4개가 무엇인지 우리는 이미 안다. 전부 `reset()` 후 push 없이 arming하는
테스트이고, **프로덕션은 그 상태에 도달하지 않는다.**

그러니 C 셀이 잰 것은 *"수정이 코드를 깨는가"*가 아니라 *"수정이 취약한 테스트를 깨는가"*였다.

차이는 C냐 Python이냐가 아니라 **테스트의 성격**이었다.

| | 1부 테스트 | 2부 테스트 |
|---|---|---|
| 출처 | 손으로 쓴 단위 테스트 | 명시적 계약에서 파생 |
| 고정하는 것 | 내부 상태기계, **도달 불가능한 상태 포함** | 계약이 요구하는 것만 |
| AI 수정에 대해 | 계속 깨짐 | 40라운드 무손상 |

계약을 줘도 안 막힌 이유가 분명하다. **헤더는 "샘플 없이도 arming이 성공해야 한다"고 말하지
않는다.** 말할 이유도 없다. AI의 가드는 계약을 위반하지 않았다. 테스트만 위반했다.

## 부산물 — 수정자는 거절할 권위를 스스로 찾는다

계약을 뺐는데 거부율은 **26%로 완전히 동일**했다. 대신 근거가 바뀌었다.

```
계약 있음:  AC 번호를 직접 인용 (대다수)
계약 없음:  AC 인용 1/8 → 코드 자신의 docstring 을 인용
```

> *"그 프로퍼티의 docstring이 실제 상태를 보고하는 것이 의도적이라고 문서화하고 있다"*

**수정자는 거절할 권위가 필요하고, 스펙이 없으면 코드 자신의 문서를 권위로 쓴다.**

그렇다면 1부의 거부 0건은 무엇이었나. 확인되지 않은 가설이 하나 있다 — 1부와 2부는 **출력
스키마**가 달랐다.

```
1부:  "addressed": [인덱스],  "declined": [{...}]   ← 거절이 선택적, 건너뛰기 쉬움
2부:  "decisions": [모든 지적이 반드시 등장]         ← 지적마다 판단 강제
```

**모든 지적에 채택/거부를 명시하도록 강제한 것**이 거부를 만든 것일 수 있다. 계약이 아니라
프롬프트 형식. 검정하지 않았으므로 가설로만 남긴다.

# 4부 — 그래서 코드가 좋아졌나

여기까지 내가 말할 수 있는 건 **"40라운드 전부 19/19"** 뿐이었다. 그런데 인수 테스트는 계약에
적힌 19개만 본다. 189건이 코드에 반영되는 동안 **계약이 말하지 않은 자리**에서 무엇이 벌어졌는지는
그 오라클이 못 본다. 이건 진짜 구멍이었다. 리뷰의 가치가 "계약 준수"에만 있다면 애초에 리뷰를
할 이유가 별로 없다.

그래서 LLM을 한 번도 더 부르지 않고, 이미 저장해둔 47개 라운드 스냅샷에 지표를 얹었다.

## 무엇으로 잴 것인가부터 정했다

"좋은 코드"를 내 취향으로 정의하면 아무 의미가 없어서, 표준과 논문에서 끌어왔다.
[ISO/IEC 25010](https://www.iso.org/obp/ui/en/#!iso:std:78176:en)의 유지보수성 하위 특성에
하나씩 지표를 붙였다.

| 무엇을 | 지표 |
|---|---|
| 계약이 승인하지 않은 동작 변경 | **차등 테스트** — v0와 vN을 같은 입력으로 돌려 트레이스 비교 |
| 분석 가능성 | **Cognitive Complexity** (Campbell 2018) |
| 시험 가능성 | **뮤테이션 점수** (인수 스위트 고정) |
| 크기 | LOC |
| 불안정성 | **상대 churn** = 누적 변경줄 ÷ 크기 |

**순환복잡도는 일부러 뺐다.** [LOC와의 상관이 0.85~0.87](https://www.scirp.org/journal/paperinformation?paperid=779)이라
크기 위에 얹는 정보가 거의 없다. 대신 읽기 비용을 재도록 설계되고
[이해 시간과의 상관이 실측된](https://arxiv.org/pdf/2007.12520) Cognitive Complexity를 썼다.
상대 churn은 [Nagappan & Ball](https://www.st.cs.uni-saarland.de/edu/recommendation-systems/papers/ICSE05Churn.pdf)이
절대 churn과 달리 결함을 잘 예측한다고 보고한 지표다.

차등 테스트가 가능한 건 이 과제가 **완전 결정적**이기 때문이다. 시간·수면·난수를 전부 주입받으므로,
시드로 300개 시나리오를 만들어 모든 판본에 똑같이 재생하면 트레이스가 같거나 다르거나 둘 중 하나다.

이번엔 **하네스를 먼저 검증했다.** (1부에서 오라클을 검증 안 한 게 이 실험 최대의 실수였다.)

```
v0 대 v0                          0/300      ✅ 결정적
지터를 상한 前에 곱하게 변경      39/300     ✅ 진짜 차이는 잡는다
주석만 변경 / 예외 메시지만 변경   0/300      ✅ 스타일은 안 잡는다
time_fn 을 두 번 더 호출 (무의미)  0/300     ✅ 구현 세부는 안 잡는다
```

## 결과 1 — 47라운드 동안 바뀐 동작은 **정확히 한 가지**였다

300 시나리오 × 47 라운드에서 나온 차이를 "무엇이 달라졌는가"로 묶으면 6개 클래스가 나오는데,
6개가 전부 같은 한 문장이었다.

```
half_open  →  open
```

쟁점은 이거 하나다. **cooldown이 지났지만 아직 아무도 호출하지 않은 열린 회로의 `state`는
무엇인가?** v0는 `"half_open"`이라고 답하고, 대부분의 수정본은 `"open"`이라고 답한다.

계약은 이걸 **정하지 않았다.** AC-13은 *"cooldown 경과 후 첫 `call()` 시점의 state가 half_open"*
이라고만 말한다. 인수 테스트도 딱 그 지점만 본다. 양쪽 다 19/19다.

솔직히 나는 이것보다 훨씬 지저분한 그림을 예상했다. 189건을 코드에 반영하면 계약 밖 어딘가는
당연히 흔들릴 거라고 생각했다. 아니었다. **리뷰 루프는 계약 밖에서도 놀랄 만큼 조용했다.**

## 결과 2 — 그런데 그 하나를 놓고 루프는 자기와 논쟁한다

`X` = v0와 다름, `.` = v0와 같음.

```
claude bare  loop1   X X X . X      ← R4에서 되돌리고 R5에서 다시 뒤집음
claude bare  loop3   X . X . X      ← 네 번 뒤집음
claude bare  loop2   X X X X X
claude structured    X X X X X ×3   (전부 R1에 결정, 이후 미동)
codex bare           . X X X X
codex structured     . . . . X      (4라운드 유지하다 마지막에 뒤집음)
무리뷰 대조          . .
```

같은 루프의 3라운드와 4라운드가 붙인 주석을 나란히 놓으면 이 실험에서 제일 할 말이 많은 장면이 된다.

> **R3** — 적극적 보고를 삭제하며:
> *"`_enter()`가 open → half-open 전이를 수행하는 유일한 지점이므로, 실제로 시험 호출이 허용된
> 동안에만 `half_open`으로 읽힌다. cooldown이 그저 경과했을 뿐인 열린 회로는 여전히 `open`이다."*

> **R4** — 그걸 되돌리며:
> *"`_enter()`가 저장된 필드를 뒤집는 유일한 지점이지만, cooldown이 이미 지난 열린 회로는 더 이상
> 아무것도 막지 않으므로 half-open으로 보고한다. 그래야 보고된 상태와 실제 동작이 일치한다."*

**둘 다 설득력 있고, 둘 다 계약을 지키고, 둘은 정반대다.** 계약이 비워둔 자리에서 리뷰 루프는
수렴하지 않는다. **진동한다.** 그리고 진동하는 동안 매 라운드가 "개선"으로 보고된다.

## 결과 3 — structured는 코드를 줄이고 bare는 늘린다

여기서 두 프롬프트가 처음으로 크게 갈렸다. 최종 라운드, v0(121줄 / cog 26 / 최악 함수 7) 대비:

| 팔 | LOC | Cognitive Complexity | 최악 함수 | 상대 churn |
|---|---|---|---|---|
| **claude structured** (3루프) | 120.7 (−0.2%) | **21.7 (−17%)** | **6.3** | 3.25 |
| **claude bare** (3루프) | 150.7 (+25%) | **32.7 (+26%)** | 10.3 | 1.52 |
| codex structured | 105 (−13%) | 24 (−8%) | 9 | 0.81 |
| codex bare | 126 (+4%) | 29 (+12%) | 7 | 0.13 |
| **수정자에게 계약을 뺀 팔** | **178 (+47%)** | **41 (+58%)** | **15** | 1.30 |
| 무리뷰 대조 | 121 | 26 | 7 | 0.00 |

세 가지가 읽힌다.

**1. 방향이 반대다.** structured 3루프는 cog −27% / −4% / −19%, bare 3루프는 +62% / +4% / +12%.
같은 모델, 같은 코드, 같은 라운드 수. 다른 건 프롬프트뿐이다.

**2. 읽기 비용이 뭉치는 자리가 다르다.** 최악 함수가 structured 6.3, bare 10.3, 계약 없는 팔 15.
Cognitive Complexity의 요점은 총합이 아니라 "한 함수를 읽을 때 머리에 몇 개를 쌓아야 하는가"다.

**3. 많이 고친 쪽이 단순해졌다.** structured의 상대 churn은 3.25 — 5라운드에 걸쳐 파일 크기의
3배 이상을 갈아엎었다. bare는 1.52밖에 안 고쳤는데 결과는 더 크고 더 복잡하다.
**"덜 건드리는 게 안전하다"가 여기선 틀렸다.**

한 가지 정직하게 붙여야 할 경고가 있다. 이 데이터에서 LOC와 Cognitive Complexity의 상관은
**r = 0.807**이다. 문헌이 순환복잡도에 대해 보고한 값과 거의 같다. 즉 위 표의 1·2는 상당 부분
*"structured가 코드를 줄였다"*의 다른 표현이다. cog가 독립적으로 보태주는 건 최악 함수의
위치 정보 정도다.

## 결과 4 — 코드 churn도 모델 성질이다. 그리고 claude 쪽은 마르지 않는다

위의 상대 churn은 5라운드 누적치다. 라운드별로 쪼개면 다른 게 보인다. 단위는 그 라운드에서
추가+삭제된 줄이고, 파일이 121줄짜리라는 걸 감안해야 한다.

```
팔                       R1   R2   R3   R4   R5    합계
claude bare  loop1       29   45   73   53   68     268
             loop2       44   27   23   20   34     148
             loop3       70   63   55   16   79     283
claude struct loop1      69   71   73   49  100     362
              loop2     101   46   58   77   72     354
              loop3     105   88   80   93   87     453
codex bare               10    6    0    0    0      16
codex structured         41   16   15    5    8      85
무리뷰 대조               0    0                      0
```

**모델 차이가 압도적이다.** structured끼리 4.6배, bare끼리 15배. claude structured는
**매 라운드 파일의 40~90%를 갈아엎는다.**

그런데 진짜 차이는 평균이 아니라 **감쇠**다.

```
codex bare        10 → 6 → 0 → 0 → 0      R3부터 파일이 바이트 동일
codex structured  41 → 16 → 15 → 5 → 8    5배 감쇠
claude bare       29 → 45 → 73 → 53 → 68  ← 오히려 증가
claude structured 69 → 71 → 73 → 49 → 100 ← 감쇠 없음
```

결과 2에서 본 지적 건수 패턴(`codex 1→1→0→0→0` vs `claude 5→6→7→6→7`)이 **코드 쪽에 그대로
찍혔다.** claude는 6개 팔 30라운드 전부에서 churn이 0인 라운드가 한 번도 없다.

**churn이 크다 ≠ 나쁘다.** claude structured는 churn 1위인데 최종 코드가 가장 작고 단순하다
(cog −17%, 최악 함수 6.3). claude bare는 churn이 절반인데 더 크고 복잡하다(cog +26%, 최악
함수 10.3). 이 데이터에서 churn은 **품질 지표가 아니라 비용 지표**다. Nagappan & Ball의
"상대 churn이 결함을 예측한다"는 여기서 재현되지 않았다 — 8개 팔은 검정 가능한 크기도 아니다.

**실무 함의**: codex 루프는 3라운드면 스스로 마르지만, claude 루프는 놔두면 5라운드째에도
파일 절반을 다시 쓴다. **라운드 상한을 거는 이유가 claude 쪽에서 훨씬 크다.**

## 결과 5 — 뮤테이션 점수는 거의 안 움직인다

고정된 23개 인수 테스트로 각 판본의 뮤턴트를 죽인 비율:

```
v0 0.867 │ claude bare 0.860 │ claude structured 0.884
         │ codex bare  0.897 │ codex structured  0.890 │ 계약 없는 팔 0.829
```

폭이 좁다(0.83~0.90). 여기서 정직하게 말할 수 있는 건 **계약이 없던 팔이 가장 낮다**는 것 정도고,
structured 대 bare의 0.024 차이는 루프 3개로 주장할 근거가 없다. 안 나온 결과도 결과라서 적는다.

다만 비율 대신 **절대 수**를 세면 하나가 튀어나온다. "아무 인수 테스트도 걸리지 않는 방식으로
이 코드를 망가뜨릴 수 있는 지점"이 몇 개인가:

```
v0                        16개
계약을 쥔 8개 팔          9 ~ 17개   (전부 그대로거나 감소)
수정자에게 계약을 뺀 팔   24개  ← +50%
```

계약 없는 팔은 57줄이 붙는 동안 **검사받지 않는 지점을 8개 같이 늘렸다.** 반면 claude bare
loop3은 42줄이 붙었는데 생존은 +1이다. 코드가 커지는 것 자체가 문제가 아니라, **계약 없이
커지는 것**이 문제였다.

이건 2×2에서 계약 가설이 기각됐던 것과 어긋나지 않는다. 계약은 *회귀를 막지* 못했지만
(그건 애초에 테스트의 성격 문제였다), *검사받지 않는 코드가 쌓이는 것*은 막았다.

# 5부 — 처방을 스스로 검정했다

여기까지 쓰고 나니 내 처방에 데이터가 없는 관절이 두 개 있었다.

```
1. 같은 코드를 독립 3회 리뷰      ← 실무 하네스는 "카테고리별 서브에이전트"를 쓴다. 안 재봤다
4. 한 번에 고친다
6. 끝낸다. 다시 리뷰하지 않는다    ← 큰 수정 뒤의 2차 배치를 한 번도 안 돌려봤다
```

실험 2 의 루프는 전부 **리뷰 1회 → 수정 → 리뷰 1회**였다. 처방은 **리뷰 3회 → 병합 → 한 번에
크게 수정**이다. 6번은 데이터가 아니라 추정이었다. 둘 다 돌렸다. 두 모델 모두.

## 실험 3 — 한 번에 고친 뒤 다시 리뷰하면

**통제군이 이 실험의 전부다.** 리뷰 1회는 볼 수 있는 것의 절반만 본다. 그래서 코드를 한 줄도
안 바꿔도 2차 배치는 반드시 "새" 항목을 낸다. 통제 없이 *"재리뷰했더니 신규 N건"*을 보고하면
그건 재리뷰의 효과가 아니라 표집 분산이다.

그래서 v0 리뷰 9개 안에서 **서로소 삼중쌍 1680쌍을 전부 열거**해 귀무분포를 만들었다.
같은 분할, 같은 정의, 신규 LLM 호출 0.

```
claude  귀무분포 (코드 무변경)   중앙값 11%   범위 0~31%
        체인1  신규율 77%
        체인2  신규율 89%
        체인3  신규율 63%

codex   귀무분포                중앙값 17%   범위 0~80%
        체인1~3  70% / 70% / 60%   (귀무분포 94~99분위)
```

claude 는 세 체인 전부 **귀무분포의 최댓값보다 두 배 이상** 높다.

**"고친 뒤에는 새로 나올 게 없다"는 틀렸다.**

### 그런데 동시에, 수정은 제 몫을 했다

"배치1 에 없다"는 사실 하나로는 세 가지가 구별되지 않아서 쪼갰다.

```
해결율    배치1 이 지적한 그룹이 배치2 에서 사라진 비율    claude 80%  codex 74%
진짜신규  v0 리뷰 9회 어디에도 없던 그룹의 비율            claude 62%  codex 37%
```

**두 결론이 같이 성립한다.** 병합해서 한 번에 넘긴 이슈의 3/4 이상이 실제로 사라졌다 —
처방의 "한 번에 고친다"는 작동한다. 그런데 배치2 지적의 절반 이상은 v0 리뷰 9회를 다 뒤져도
없던 것이다.

### 이유는 "리뷰어가 더 잘 봐서"가 아니었다

```
        수정 churn(줄)   진짜 신규율
claude c2     143            82%
claude c1      87            62%
claude c3      82            43%
codex  c1      36            50%
codex  c2      28            40%
codex  c3      36            20%
                   r = 0.837  (n = 6)
```

**신규율은 수정이 건드린 줄 수로 대부분 설명된다.** 재리뷰가 새 지적을 내는 이유는 리뷰어가
2차에 똑똑해져서가 아니라 **아직 아무도 리뷰하지 않은 코드가 생겼기 때문**이다.

이건 처방을 뒤집는 게 아니라 정확하게 만든다.

> 재리뷰의 필요는 *"리뷰가 수렴했는가"*의 문제가 아니라 **"새로 쓴 코드를 봤는가"**의 문제다.
> 수정이 작으면 재리뷰의 수확도 작다. 수정이 파일 절반을 다시 썼으면 그건 재리뷰가 아니라
> **새 코드에 대한 첫 리뷰**다.

*(n = 6 이라 상관계수 자체를 강하게 주장하진 못한다. 방향과 크기만 적는다.)*

### 덤 — 한 번에 크게 고치면 반복보다 복잡해진다

같은 v0, 같은 프롬프트, 같은 모델. 다른 건 수정을 한 번에 하느냐 다섯 번에 나눠 하느냐뿐이다.

```
                              LOC   cog   최악함수   총 churn
v0                            121    26      7           0
claude 한번에 크게 고침         123    29     10         104
claude 5라운드 루프             121    22      6         390
codex  한번에 크게 고침         117    26      8          33
codex  5라운드 루프             105    24      9          85
```

4부의 *"많이 고친 쪽이 단순해졌다"*와 같은 방향이다. 루프는 자기가 어제 붙인 것을 오늘 걷어낼
기회를 갖는다. 한 방에 고치면 그 기회가 없다. **준수율은 40라운드 전부 19/19로 동일하다** —
이 차이는 계약이 아니라 유지보수성에서만 난다.

## 실험 4 — 리뷰어를 카테고리별로 쪼개면

우리 `/review`도, 시중 하네스도 대개 팬아웃이다. 보안·성능·동시성 리뷰어를 각각 띄우고 마지막에
합친다. 그런데 실험 2 는 **단일** structured 호출만 쟀다.

세 팔을 뒀다. 대상은 전부 v0.

```
A  단일 structured 1콜
B  6개 카테고리를 6개 콜에 쪼개 병합
C  동일 structured 6콜을 병합          ← 결정적 통제
```

**C 가 없으면 무의미하다.** B 대 A 는 "6콜이 1콜보다 많이 찾는다"이고 그건 이미 아는 사실이다.
**B − C 만이 쪼개는 것 자체의 효과다.**

프롬프트는 손으로 6개 쓰지 않고 structured 원본에서 **기계적으로 파생**시켰다. 바뀌는 건
6영역 → 1영역, 그리고 "중요도 순으로 나열" 한 줄 삭제. 출력 스키마·15건 상한·**"찾을 게 없으면
빈 배열을 반환하라"** 문구는 바이트 단위로 유지했다. 마지막 게 특히 중요한데, 그걸 지우면
전문 리뷰어에게 *"네 영역에서 뭐라도 말해라"*라고 시키는 것이고, 그러면 팬아웃의 지적 증가는
측정이 아니라 내가 만든 것이 된다.

### 결과 — 내 예측이 틀렸다

```
claude                콜   고유 이슈   원시 지적   중복률   콜당 고유
A 단일 structured      1     11.0        11.6      1.0배     11.0
C 동일 structured 6콜   6     19.7        69.3      3.6배      3.3
B 카테고리 6콜          6     30.0        54.7      1.8배      5.0

codex
A 단일 structured      1      2.8         2.8      1.0배      2.8
C 동일 structured 6콜   6      6.5        16.7      2.6배      1.1
B 카테고리 6콜          6      7.7        10.0      1.3배      1.3
```

**같은 6콜인데 고유 이슈가 claude +52%, codex +18%.** 그리고 **원시 지적은 오히려 21% 적다.**
사람이 훑을 항목이 줄면서 발견은 늘었다.

나는 정반대를 예측했다. *"각 전문가가 자기 영역에서 뭐라도 말해야 하니 총량은 늘고 신호 대
잡음은 나빠질 것"*이라고 썼다. 총량은 줄었고 신호는 늘었다.

### 이득이 어디서 오는가 — 일반 리뷰어가 robustness 를 짜내고 있었다

v0 structured 리뷰 **9회가 한 번도 언급하지 않은** 그룹을 카테고리별로 세면:

```
claude   robustness  10개  (major 4 / minor 6)
         naming       8개  (major 2 / minor 6)
         style        3개
         design       1개
         functionality · complexity   0개    ← 일반 리뷰어가 이미 다 본다

codex    robustness   2개  (둘 다 major)
         complexity   1개 · naming 1개
```

새로 나오는 건 전부 **robustness · naming · style** — 일반 리뷰어가 *"중요도 순으로 나열하고
15건까지"*라는 지시 아래에서 **잘라내는** 영역이다.

### 그래서 그 추가분은 진짜인가 — 판정해봤다

"고유 이슈"는 서로 다른 그룹의 개수지 **가치 있는** 그룹의 개수가 아니다. 그래서 팬아웃만
찾은 21건과 **양쪽 다 찾은 18건을 섞고 순서를 섞어** 라벨 없이 39건을 만들었다. 공통군이
내부 통제군이다. 정답 키를 열기 전에 소스와 대조해 판정하고 확정한 뒤 채점했다.

```
전체 39건   REAL 12 (31%)   STYLE 27 (69%)   WRONG 0   OUT 0

            n   REAL   비율
팬아웃 배타 21     8    38%
양쪽 공통   18     4    22%        Fisher 단측 p = 0.236
```

**제일 놀란 건 WRONG이 0이라는 것이다.** 39건 전부 코드에 대한 사실 주장이 정확했다.
리뷰어는 없는 걸 지어내지 않았다. 대신 **69%가 이름·주석·구조** 지적이었다.

> 글의 톤은 둘 다 아니었다. *"리뷰가 일감을 만든다"*도 *"계속 실재를 찾는다"*도 아니고,
> **정확하지만 대부분 사소하다.**

배타군의 REAL 비율이 더 높긴 하다. 하지만 **p = 0.236이라 주장할 수 없다.** 경계선 7건을
최악으로 뒤집어도 방향만 유지될 뿐이다.

그리고 **리뷰어의 severity 자평은 절반만 맞았다** — 배타 `major` 7건 중 내 판정 REAL 4건,
공통 `major` 8건 중 4건. severity를 그대로 인용하면 안 된다.

*(판정자는 이 +52%를 발표한 당사자다. 키에는 블라인드였지만 가설에는 아니고, 기준도 내가
정했다. 나를 모르는 사람이 같은 39건을 판정해 방향이 재현되어야 인용 가능하다.)*

*(단, 지적의 진위는 판정하지 않았다. "고유 이슈"는 서로 다른 그룹의 개수지 가치 있는 그룹의
개수가 아니다. major 라는 것도 리뷰어가 스스로 매긴 것이다. 그리고 codex 의 한 반복은
naming 호출이 malformed 로 실패해 5콜이다 — 재시도 금지 원칙대로 기록만 하고 뒀다.)*

## 덤 — 성긴 계약으로 다시 재보니 논지가 좁아졌다

*"계약이 비워둔 자리에서 진동한다"*를 **일반화하려고** 두 번째 과제를 만들었다. 비슷한 크기를
**19 AC가 아니라 8 AC로만** 덮은 TTL 캐시. 자유 영역 8개를 예측해 **구현이 존재하기 전에**
등록하고 커밋했다.

```
독립 3구현 (claude)  →  전부 8/8 통과, 차등 테스트 0/400 (셋이 완전히 같음)
10라운드 루프        →  AC 8/8 전부 유지, 차등 0/400  ← 자유 영역을 하나도 안 움직임
```

하네스 고장이 아니다. 자유 영역 선택을 하나씩 뒤집으면 95/400, 400/400, 369/400으로
**전부 잡는다.**

그리고 이 실험의 가장 큰 구멍이 하나 있었다 — 셋 다 claude면 "관례"인지 "한 모델의 습관"인지
구별이 안 된다. **codex 구현을 하나 더 붙였다.**

```
codex   8/8 통과 · 54줄        ← claude 는 138 / 133 / 101줄
6쌍 전부 0/400                 (claude↔codex 3쌍 포함)
```

**크기가 2.5배 차이인데 400 시나리오에서 동작이 완전히 같다.** 서로 다른 회사의 모델이,
계약이 비워둔 자리에서 같은 답을 골랐다. 세 구현 다 `notes`에 *"여기가 모호했다"*를 스스로
적었고, 적은 자리는 내 예측과 겹쳤는데, **고른 답이 같았다.**

결정적인 건 그 다음이다. **관례가 약한 자리에서는 codex도 갈린다.**

```
             capacity='2'   ttl=None    time_fn=5
claude1·2    TypeError      TypeError   TypeError
claude3      ValueError     ValueError  ValueError
codex        TypeError      TypeError   검증 안 함    ← 세 번째 답
```

계약은 *값*이 잘못된 경우만 정하고 *타입*은 말하지 않는다. 그리고 "잘못된 타입에 무엇을
던지나"에는 널리 합의된 관례가 없다.

```
관례 강함 (TTL 경계·LRU 갱신·len 의미)  →  4구현 전부 일치, 차등 0/400
관례 약함 (타입 오류 처리)              →  4구현이 3가지 답
```

**한 실험 안에서 두 조건이 정반대로 갈린다.** 이 연구에서 관례 가설을 지지하는 가장 뾰족한
증거다.

루프도 같았다. claude 2루프 + codex 1루프, 15라운드에 지적 104건이 반영됐는데 **세 루프 전부
차등 0/400**이다. 그러면서 코드는 103줄에서 85~90줄로 줄었다.

```
                최종 loc   cog   누적 churn   생존 뮤턴트
v0                 103      19        0        11 / 84
claude loop1        90      14      323        14 / 67
claude loop2        87      12      418        10 / 52
codex  loop         85      17      137         8 / 83
```

**지적을 100건 넘게 반영하고 코드를 15% 줄이면서 관측 동작은 한 번도 안 바꿨다 — 순수
리팩터링이다.** 그리고 codex의 churn이 claude의 1/3이다. 뮤테이션은 방향이 갈린다 —
claude는 코드를 **덜어냈고**(뮤테이션 지점 84 → 67·52) codex는 표면을 유지하며 **조였다**
(생존 11 → 8).

그래서 논지가 좁아진다.

> **진동은 계약의 성김이 만드는 것이 아니다. 관례의 부재가 만든다.**

`half_open`의 상태 보고 시점에는 합의된 관례가 없다 → 진동했다. TTL 경계·LRU 갱신·`len`의
의미에는 관례가 강하다 → 계약이 훨씬 성긴데도 아무도 안 움직였다. 이 문장은 **반증 가능**하다:
진동하는 자유 영역은 **사람도 의견이 갈리는 자리**여야 한다.

# 6부 — 오탐을 어떻게 줄이는가

1부의 판정에서 가장 불편한 숫자가 나왔다. **오탐 4건이 전부 발견빈도 상위권이었다.**

```
오탐 4건의 평균 발견빈도   6.8 / 10
진짜 10건의 평균 발견빈도  3.4 / 10
```

그리고 오탐 넷 다 같은 종류였다 — **호출자·초기화 경로·스레드를 봐야 아는 주장.**
리뷰어에게는 파일 하나뿐이었으니 확인할 방법이 없었다. 그래서 물었다.

> 리포를 열어주면 어떻게 되나?

## 문단 하나만 바꿨다

같은 코드, 같은 프롬프트, 같은 10회. 바뀐 건 이것뿐이다.

```diff
-너에겐 다른 파일도, 리포지토리도, 테스트도, 도구도 없다.
+프로덕션 소스 트리가 /home/noel/spoton/src 에 읽기전용으로 마운트돼 있다.
+Read 와 Grep 으로 호출자·헤더·초기화 경로·스레딩을 확인하고 나서 결함을 주장해라.
```

여기 함정이 하나 있었다. **이 리포의 `work-docs/` 에 이 실험의 판정 결과가 들어 있다.**
정답지가 리포 안에 있는 것이다. 그래서 `src/` 만 마운트하고 카나리를 양방향으로 돌렸다 —
`sensor.c` 는 읽히고 판정 파일은 안 읽혀야 통과.

## 결과 — 오탐이 전멸했다

```
                 지적   고유 결함   진짜   오탐    정밀도
파일만 (1부)       61      14        10     4      71%
src/ 열림          30       7         7     0     100%
```

**D02(8회) D03(7회) D04(7회) D07(5회) — 네 개가 하나도 안 나왔다.**

지적 총량도 절반으로 줄었다(61 → 30). critical 은 2 → 0. **말을 아끼면서 오탐을 버렸다.**

## 그리고 파일만으로는 불가능한 결함 3개를 새로 찾았다

전부 다른 파일의 사실이 있어야 성립하는 것들이다. 세 건 다 소스로 검증했다.

**① 링에 시간 구멍이 남는다 (10/10회 발견)**
FIFO 오버플로 시 `force_expire()` 를 부르는데, 그 함수는 `if (!armed) return false;` 로
**즉시 반환**한다. 무장 안 된 상태가 흔한 경우다. **링 히스토리는 손대지 않는다.**
다음 임팩트의 pre-roll(최대 0.9초)이 그 구멍을 가로지르고, 잔존 검사는 **연속성을 증명하지
않는다.** takeback·tempo 가 128 ms 짜리 시간 구멍 위에서 계산돼 저장된다.

**② 앞 스윙이 뒤 스윙의 키로 기록된다 (4/10)**
임팩트 디바운스는 500 ms 인데 pre-roll 은 **903 ms**. 디바운스보다 길다.
세그먼터는 첫 확정 임팩트에서 멈추고, 파이프라인은 거기에 **새 임팩트의 join key** 를 찍는다.

**③ 50 Hz 샘플에 1000 Hz 라벨 (2/10)**
저전력 진입이 accel 을 50 Hz 로 낮추고 자이로를 끄는데 **FIFO 설정은 안 건드린다.**
샘플레이트는 컴파일타임 상수로 찍힌다. 가방 속에서 라켓이 부딪히면 20배 틀린 시간 지표가
기록된다.

## 🎯 합의가 다시 정보를 갖는다

```
파일만 조건에서 가장 많이 발견된 것들   →  오탐 (8, 7, 7, 5회)
리포 열린 조건에서 가장 많이 발견된 것  →  ①번, 10/10, 진짜
```

이유가 구조적이다. **한 파일만 보고도 여러 리뷰어가 똑같이 확신할 수 있는 것은,
그 파일 밖에서 반증되는 것이다.** 합의는 "진짜라서"가 아니라 **"같은 정보 부족을 공유해서"**
생긴다. 확인할 수단이 생기는 순간 그 상관이 뒤집힌다.

이건 실무에 바로 걸린다. 대부분의 AI 리뷰 하네스는 **diff 만** 주고, 그 다음
**여러 리뷰어가 동의한 것을 통과**시킨다. 내 데이터에서 그 조합은 **오탐을 우선 선별하는
규칙**이다.

## 대가는 재현율이다

공짜가 아니다. 진짜 10건 중 6건이 사라졌다.

```
              정밀도       재현율
파일만         71%          77%
src/ 열림     100%          54%
```

사라진 것들은 도달성이 낮거나(49일 가동 필요), 관측성 지적이거나, 컴파일러 최적화 수준의
논증이었다. 리포를 읽은 리뷰어는 *"실제로 일어날 수 있는가"* 를 확인하고 **말을 아꼈고**,
그 필터가 오탐과 함께 희미한 진짜도 걸렀다.

> **둘 다 갖고 싶으면 두 조건을 다 돌리면 된다. 합집합이 13/13이다.**
> 20콜이고, 오탐 4건은 리포-열림 쪽 결과가 자동으로 반증한다.

*(복합 레버라는 점은 짚어둔다 — 마운트·Read/Grep·권한모드를 함께 켰고 분리하지 않았다.
그리고 판정자는 나다.)*

# 7부 — 내 처방을 처방대로 돌려봤다

여기까지 쓰고 처방을 정리했다. 그리고 동료가 물었다. *"그걸 왜 다 반영해서 돌려본 게 아니지?"*

맞는 지적이었다. 각 항목은 **따로따로** 측정됐고, 전부 켠 조건은 한 번도 돌린 적이 없었다.
그래서 두 번 돌렸다. 그리고 **내 처방에서 두 개가 반증됐다.**

## 먼저 — "전부 반영" 이라는 열은 애초에 성립하지 않았다

사전등록 단계에서 적용 가능성부터 감사했다.

```
구조화 프롬프트   ⚪ 이미 상수였다 — 1부와 리포-접근 조건 둘 다 structured 였다.
                     두 프롬프트는 문단 하나만 다르다 (diff 로 확인)
계약 먼저         ❌ 이 C 모듈에 성문 계약이 없다. 동결 테스트를 계약으로 주면
                     판정 기준과 독립성이 깨진다 (오라클 누설)
codex 로도        ❌ codex-linux-sandbox 부재로 리포 접근 조건 자체가 불가
배치수정·churn게이트  루프 전용 — 리뷰 단독 조건에 해당 없음
```

**내 비교표가 과장돼 있었다.** 처방 절반은 루프 전용이었고 하나는 이미 양쪽 팔에 들어 있었다.
18번째 축소다.

## 실험 8 — 리포 접근 위에 팬아웃을 얹으면 재현율이 돌아오는가

리포 접근은 오탐을 0으로 만든 대신 재현율을 잃었다(77% → 54%). 잃은 것들은 전부 **저빈도**
진짜 결함이었다 — 실험 4가 보여준, 팬아웃이 살려내는 바로 그 자리다.

프롬프트는 손으로 쓰지 않고 기계 파생했다. 스키마의 `category` enum 을 값 하나로 좁히고
배정 렌즈 한 줄을 넣은 것이 전부다. **15건 상한과 `{"findings": []}` 허용 문구는 바이트
그대로 뒀다** — 후자를 지우면 렌즈마다 "뭐라도 말해라"는 압력이 걸리고, 그러면 팬아웃의 증가는
측정이 아니라 프롬프트가 만든 것이 된다.

예측 다섯 개를 **돌리기 전에 동결**했다(`PREREG-composite-fanout-repo.md`).

| | 예산 | 고유 | 재현율 | 정밀도 | 오탐 |
|---|---|---|---|---|---|
| 파일만 · 단일 | 10콜 | 15 | 79% | 73% | 4/4 |
| 리포 · 단일 | 10콜 | 8 | 50% | **100%** | **0/4** |
| **리포 · 팬아웃** | 30콜 | **16** | **79%** | 92% | 1/4 |
| 리포 · 팬아웃 (부분) | 10콜 | 9 | **43%** | **100%** | **0/4** |

> 통합 풀 193건, ARI 0.963 PASS. 참값 분모는 이 풀의 입도로 14다 — 앞서 6부에서 13이라 쓴
> 것과 다른데, 조건 차이가 아니라 클러스터 입도 차이다. 같은 기준으로 다시 재면 리포·단일의
> 재현율은 50%다.

예측 다섯 중 넷이 맞았다. **다섯 번째가 틀렸고 그게 중요한 쪽이다.**

```
P5  "같은 예산에서도 팬아웃이 우세할 것"   →  43% vs 50%   FAIL
```

**재현율 이득은 팬아웃의 구조가 아니라 예산 3배에서 왔다.** 같은 10콜에서는 오히려 단일
리뷰어가 조금 나았다.

이건 실험 4(Python, 같은 예산에 고유 +52%)와 어긋난다. 유력한 설명은 **렌즈가 서로 겹친다**는
것이다 — C 펌웨어에서 `concurrency-lifetime` 렌즈가 10개 그룹을 냈는데 그 렌즈에만 있는 건
2개다. Python 의 design·naming·style 은 훨씬 깨끗하게 분리된다.

> **팬아웃이 공짜로 낫다는 주장은 이 데이터로 할 수 없다.** 축이 실제로 분리되는 대상에서만
> 성립한다.

### 저빈도 결함 회복은 진짜였다

```
       판정    파일만   리포단일   리포팬아웃      (발견 유닛 / 10 · 10 · 6)
D11    진짜      1        3          6      ★ 10회 중 1회 → 6유닛 전부
D08    진짜      3        0          4
D10    진짜      2        0          3
D13    진짜      1        0          2
D03    오탐      7        0          1      ← 되살아났다
D09    진짜      3        1          0      ← 유일하게 잃은 것
```

리포 단일이 0/10 이던 저빈도 진짜들을 팬아웃이 전부 회복했다.

### 그런데 오탐이 하나 되살아났고, 어느 렌즈인지 안다

D03 이다. **1부의 4/4 회귀를 만든 바로 그 지적**이고, 리포를 열자 0/10 으로 사라졌던 것이다.
팬아웃에서 1/6 으로 돌아왔고 **`state-invariant` 렌즈 하나에서만** 나왔다.

기전이 설명된다. *"이 모듈의 상태 불변식만 보라"* 는 배정은 **시선을 모듈 안에 가둔다.**
그런데 그 지적을 반증하는 사실은 `sensor.c`, 모듈 밖에 있다.

> **렌즈 배정과 리포 접근은 서로 당긴다.** 리포 접근은 "밖을 봐라"이고 렌즈 배정은
> "네 영역만 봐라"이다. 겹치면 후자가 전자를 침식한다.

그리고 여기서 **내 처방 두 개가 충돌한다.** 1/6 이니 "합의 2회 이상"으로 걸렀으면 사라졌을
텐데, 처방 3번이 정확히 *"합의 횟수를 진위의 대리변수로 쓰지 마라"* 다. 같은 데이터셋 안에서
두 규칙이 반대 방향을 가리킨다. **이 조합의 필터 규칙은 아직 없다.**

## 실험 9 — 처방 전체를 루프로 (사람 선별만 제외)

처방 원문을 다시 읽으니 0번 헤드라인이 **"리뷰는 여러 번, 수정은 한 번"** 이었다. 5라운드
루프는 내 처방이 *하지 말라*는 것이었다. 그러니까 "전부 반영"은 100콜짜리가 아니다 —
팬아웃 리뷰, 묶기, **한 번** 수정, 측정, churn 게이트다.

8단계 중 **7개를 켰다.** 뺀 것은 *"사람이 훑는다"* 하나인데, 그건 처방 스스로
**"자동화하지 않는다"** 고 못박은 단계다. 그래서 **이 실행은 처방의 상한이 아니라 하한이다.**

수정자에게는 이번에 처음으로 **테스트를 읽게 했다**(읽기전용 마운트라 편집은 지시가 아니라
구조로 막힌다) — 처방의 *"테스트 실행은 열고 편집은 막는다"* 를 툴체인 없이 근사한 것이다.
카나리 4방향 PASS: `tests/` 읽힘 · `src/` 읽힘 · 정답지 차단 · 테스트 쓰기 불가.

| | 완료 라운드 | RED | 그 4개 회귀 | 빌드 실패 |
|---|---|---|---|---|
| 1부 · 파일만 · 단일 | 15 | 12 (80%) | 4개 전부 | 0 |
| 리포 · 단일 | 10 | 6 (60%) | 0회 | 4라운드 |
| **처방 전체** | 4 | **0 (0%)** | 0회 | **0회** |

### 그런데 처방의 정지 규칙이 발화하지 않았다

처방 7번은 이렇게 적혀 있었다. *"멈추는 기준은 '지적이 0'이 아니라 'churn 이 0 에 수렴'이다."*
임계값 5줄을 **돌리기 전에 코드에 박아뒀다.**

```
churn   194  →  262  →  395      단조 증가. 임계 5 에 근처도 못 감
지적      9  →    9  →   10  →  0   ← 여기서 멈췄다
```

**루프는 내 처방이 명시적으로 기각한 기준으로 종료됐다.**

처방이 틀렸다기보다 **검정된 적이 없었다.** churn→0 수렴은 2부(Python, **계약 있음**)에서 온
관찰이고 거기선 코드가 156→137줄로 줄었다. 계약이 없는 C 모듈에서는 수렴 방향 자체가 반대다.

> **정지 규칙은 무조건이 아니라 조건부다.** 계약이 자유 공간을 닫아둔 곳에서만 churn 이 0 으로
> 간다. 계약이 없으면 리뷰는 계속 새 자리를 찾아내고 churn 은 증가한다. **19번째 축소다.**

### 대가 — 코드가 가장 빠르게 불었다

```
동결 원본 359줄

1부   루프2   505 → 683 → 753 → 770 → 951    (5R, +88%)
리포  루프2   513 → 678 → 706 → 859          (4R, +68%)
처방  루프2   485 → 687 → 904                (3R, +152%)
라운드당        +126   +202   +217              ← 가속
```

**준수만 보면 처방 전체가 압도적이고(4/4 GREEN), 크기를 같이 보면 가장 나쁘다.** 처방 6번이
*"준수율 옆에 크기를 같이 찍어라"* 라고 한 이유가 이것인데, 그 처방의 가장 좋은 사례가
**이 실험 자신**이 됐다.

### ★ 6부의 세 번째 실패 유형이 사라졌다 — 예상과 다른 경로로

6부에서 한 루프가 전 라운드 빌드 실패였던 것을 기억하자. 수정자가 모듈 밖
`power_sampling_active()` 로 **정당한** 수정을 했는데 테스트가 그 모듈만 링크한 것이었고,
나는 해법으로 **"오라클의 범위를 넓혀라"** 를 적었다.

실험 9 에서는 **오라클을 하나도 안 건드렸는데 빌드 실패가 0회다.** 수정자가 스스로 거절했다.

> *"the fix here would require editing a test."*
> *"the tests pin the effective ring capacity, so I cannot enlarge it."*
> *"Real, but not fixable inside this file — known only to `sensor.c`."*

**테스트를 읽게 하고 편집을 막은 것이, 오라클을 넓히는 것과 같은 일을 했다.** 그리고 훨씬
싸다 — 빌드 시스템을 안 건드린다.

다만 정직하게: **고친 게 아니라 미룬 것이다.** 거절 12건 중 다수가 *"real but out of scope"*
다. 유계 손상(빌드 실패)과 무한 defer 의 교환이고, 어느 쪽이 나은지는 이 데이터가 답하지 않는다.

```
거절률   2부 (Python, 계약 있음)   20~26%
        실험 9 (C, 계약 없음)      34%   (2/7 · 3/9 · 4/9 · 3/10)
```

### 재현된 수치 하나

```
묶기   15→7   18→9   15→9   17→10       중복배수 1.86
실험 4  "팬아웃은 1.8번 말한다"           ← 다른 대상·루프 조건에서 재현
```

이 연구에서 **대상을 바꿔 재현된 몇 안 되는 수치**다.

### 이 실행의 n 은 4가 아니다

완료 4라운드 중 한 루프가 2라운드에서 수정 응답이 깨져 죽었다(재시도 금지 원칙대로 기록만 하고
안 늘렸다). **실질 독립 관측은 1.25 루프다.** 그리고 사람 선별을 뺀 것이 결과를 낙관 쪽으로
민다 — 사람이 그 34% 거절분을 미리 걷어냈다면 churn 이 훨씬 작았을 테고, 그러면 정지 규칙이
발화했을 수도 있다.

# 8부 — 두 개를 더 열었다

남은 과제 목록에서 둘을 골랐다. **codex 로도 재현되는가**, 그리고 **"계약"이라 부른 것이
사실 무엇이었는가**.

## 먼저 — codex 가 못 돌린 이유는 codex 가 아니었다

6부에서 *"codex 는 이 조건을 돌릴 수 없다, `codex-linux-sandbox` 가 설치 어디에도 없다"*
고 적었다. 이번에 stderr 를 끝까지 읽었다.

```
WARNING: proceeding, even though we could not create PATH aliases:
  Refusing to create helper binaries under temporary dir "/tmp"
```

codex 는 그 헬퍼를 **패키지로 배포하지 않고 실행 시점에 만든다.** 그리고 임시 디렉터리
아래에는 만들기를 거부한다. 경고만 남기고 진행한 뒤, 셸 명령을 돌릴 때 없는 헬퍼를 부르며
죽는다. **내가 스크래치를 `/tmp` 에 둔 것이 원인이었다.**

> **같은 실수가 세 번째다.** ① "codex 는 도구를 못 막는다 → 능력 비대칭" — 실제로는 codex
> 셸이 고장나 있었다. ② "헬퍼 부재 = 설치 결함" — 실제로는 스크래치가 `/tmp` 라서.
> ③ ②의 정정 자체도 절반만 맞았다. **셋 다 "모델의 성질" 로 기록될 뻔한 것이 "내 설정"
> 이었다.**

## 오탐 제거는 모델을 넘어 재현됐다

통합 풀 128건, **ARI 0.978 PASS**, 대조군 빈도까지 정확 복원.

```
      판정     대조군  E7-claude  E7-codex
D02   오탐       8        0          0
D03   오탐       7        0          0
D04   오탐       7        0          0
D07   오탐       5        0          0
D09   진짜       3        1         10   ★
D11   진짜       1        3          0   ★
D14   진짜       1        0          6   ★
──────────────────────────────────────
오탐 재현               0/4        0/4
대조군 진짜             4/10       4/10   (합집합 5/10)
```

**서로 다른 회사의 모델이, 같은 문단 하나를 바꿨을 때, 같은 오탐 4건을 똑같이 버렸다.**
이 연구에서 모델을 넘어 재현된 가장 중요한 결과다.

그런데 **경로가 정반대다** — claude 61→30지적(−51%, 말을 아낌), codex 27→37(+37%, 말이 늚).
보는 데도 다르다: D09 를 claude 는 1/10 으로 겨우 봤는데 codex 는 10/10 전부가 봤다.

## "계약" 이라 부른 것은 사실 두 가지였다

프롬프트 diff 를 뜯어보니 이랬다.

```
A  손대지 마라 (리팩터·리네임·리포맷 금지)      양쪽 팔 모두 — 상수, 측정 안 됨
B  공개 표면이 계약이고 고정이다                 계약 팔에만
C  그 계약의 내용 (SPEC 19 AC)                  계약 팔에만
```

**B 와 C 를 따로 준 팔이 없었다.** 가운데 셀 하나만 새로 돌렸다.

| | 지적 | 거부 | 최종 LOC | 누적 churn | AC |
|---|---|---|---|---|---|
| A 손대지마라만 | 31 | 8 (26%) | 254 | 195 | 19/19 |
| **A+B 범위 고정** | 34 | **17 (50%)** | 237 | **136** | 19/19 |
| A+B+C SPEC | 31 | 4~12 (26%) | **202** | 191 | 19/19 |

**LOC 는 계단을 이룬다**(254 > 237 > 202). 스펙 없이 한 줄로 −7%, **churn 은 A+B 가 최저.**

**그런데 거부율은 계단이 아니다** — 26% → **50%** → 26%. AC 번호 인용이 A+B 는 17건 중 0건,
A+B+C 는 12건 중 7건이다. *"고정이다"* 라고 들었는데 확인할 문서가 없으니 애매하면 전부
거절한다.

> **B 는 팽창을 막고, C 는 판단을 교정한다.** 4부의 "계약이 87% 를 고정했다" 는 대부분
> B 의 효과다.

# 9부 — 무한 리뷰를 벗어나는 법

정지 기준으로 쓸 만한 것이 넷 있었는데 **셋이 탈락했다.**

```
① churn → 0        계약 있는 과제에서만 발화. 없으면 194→262→395 로 증가
② 지적 0           7부에서 실제로 루프를 끝낸 것. 그런데 내 처방이 기각한 기준
③ 라운드 상한       1·6부가 쓴 것. 수렴이 아니라 절단이다
④ 애초에 루프를 안 돈다   ← 남는 건 이것뿐
```

| | 진짜 결함 커버리지 | 코드 변화 |
|---|---|---|
| 리뷰만 1회 | 34% | 없음 |
| 리뷰만 3회 | 61% | 없음 |
| 리뷰만 5회 | **76%** | 없음 |
| 리뷰-수정 루프 5R | 준수율 불변 | **+24~152%** |

**이득은 전부 리뷰 쪽에, 위험은 전부 수정 쪽에 있다.** 둘을 한 사이클로 묶으면 이득당
위험이 최대가 된다 — 그게 대부분의 auto-fix 하네스다.

같은 예산을 어디에 쓰는가:

```
30콜을 루프에 쓴다   1부 15라운드   →  RED 12/15, 코드 +88%, 4/4 회귀(=오탐이 만든 것)
30콜을 리뷰에 쓴다   8부 팬아웃     →  코드 무변경, 고유 결함 16개, 정밀도 92%
```

## 실측 비용

```
                            콜   합산시간   평균/콜   응답    코드 위험
1부 루프 (파일만, 15R)       30   172분     344초   544KB    +88%
6부 루프 (리포, 10R)         20   189분     567초   384KB    +68%
7부 루프 (처방 전체, 4R)     29   222분     459초   305KB   +152%
대조군 리뷰 10회             10    45분     268초    85KB       0
리포 리뷰 10회               10    79분     474초    59KB       0
팬아웃 30콜                  30   200분     400초   222KB       0
```

합산 시간은 동시 실행이라 사용자 대기시간이 아니다. 평균/콜이 실제 한 번의 대기다.
그리고 **토큰은 기록하지 않았다** — 입력(코드 + 누적 지적)이 라운드마다 커지므로 실제
토큰 비용은 여기 적힌 것보다 가파르게 오른다.

> **파일이 커지는 것 자체가 정지 요인이 된다.** 6부의 R4 리뷰 두 건이 900초 상한에 걸려
> 죽었다. 900줄짜리 파일에 리포 탐색을 얹으면 15분을 넘긴다. 루프를 오래 돌리면 코드가
> 커지고, 코드가 커지면 리뷰가 느려지고, 결국 **수렴이 아니라 타임아웃으로 끝난다.**

# 그래서 몇 번 돌려야 하나

처음 질문에 대한 답은 이렇게 바뀌었다.

**1. "이제 됐냐"의 답은 리뷰어마다 다르고, 답을 준다고 다 본 것도 아니다.**
codex는 두 팔 다 지적이 감소했고 bare는 3라운드에 완전히 침묵했다. claude는 두 팔 다 15라운드를
돌려도 감소조차 없다. 준수율은 넷 다 같다. **끝을 아는 것은 모델 성질이다.**

다만 침묵을 완주 신호로 읽으면 안 된다. 침묵한 codex bare는 5라운드 동안 2건만 봤고, 같은 코드에서
codex structured는 시계 실패·프로세스 제어 예외·wedge 같은 계열을 계속 찾아냈다. **멈추는 리뷰어가
더 나은 리뷰어라는 보장은 없다.**

**2. 한 번은 확실히 부족하다.** 세 가지 다른 조건에서 전부 "절반"이 나왔다. 그리고 어떤 결함은
10번 중 1번만 잡힌다.

**3. 지적이 줄어드는 것을 진척으로 읽으면 안 된다.** 1부에서는 코드가 나빠지는 동안에도 지적이
줄었다. 그리고 줄어드는 이유의 일부는 AI가 스스로 쌓아 올린 설명 주석이었다 — 로직은 그대로 두고
주석만 걷어내니 지적이 2.8배로 돌아왔다.

그 추가분 11건도 판정했다. **진짜 6 · 오탐 3 · 판단불가 2.** 주석은 오탐을 걸러주기보다
**실제 결함을 더 많이 가리고 있었다.** 그리고 가려진 것 중 가장 심각한 것이 압권이다 —
루프가 앞선 라운드에서 *"staleness를 더 엄격히 하자"*며 추가한 `gen_floor` 기계장치가,
정상 운영 중 아무것도 그것을 전진시키지 않아서 **장기 가동의 절반 동안 스윙 캡처를 통째로
죽이는** 구조였다. 원본에는 없던 코드다.

> **루프가 만든 버그를, 루프가 만든 주석이 가리고 있었다.**

**4. 수정을 시킬 때 지적만 주지 말고 계약을 같이 줘라.** 계약이 없으면 거부 0건에 회귀 4/4,
있으면 거부 26%에 회귀 0. 이게 이 실험에서 가장 실행 가능한 처방이다.

**5. 테스트 없이는 이 중 아무것도 안 보인다.** 나는 정답지 없이 재보려 했고 실패했다.
"지적이 방금 고친 줄에 있는가"는 diff 산수로 계산되지만, fix가 파일의 3분의 1을 다시 쓰면
우연 수준이 60%가 되어 신호가 익사한다. 12개 라운드 관측이 0.0~4.3으로 흩어졌다.

# 나라면 이제 이렇게 리뷰하겠다

이 코드에서 나온 숫자로 정리한 실제 레시피다. 데이터가 뒷받침하는 것과 내 판단인 것을 표시해
둔다.

## 0. 가장 큰 것 — 리뷰 반복과 수정 루프는 다른 일이다

이게 이 실험 전체에서 가장 강한 처방이다.

| | 이득 | 비용 |
|---|---|---|
| **리뷰만 반복** | 진짜 결함 커버리지 **34% → 61% → 76%** | 없음. 코드가 안 바뀐다 |
| **리뷰-수정 루프 반복** | **0.** 40라운드 준수율 불변 | 코드 **+24~63%**, 1부에선 테스트 파손 |

**[데이터]** 커버리지 곡선은 세 가지 다른 조건에서 재현됐다. 루프의 이득 0은 2부 40라운드에서
직접 측정했다.

두 번째를 하면서 첫 번째의 이득을 기대하는 것 — 그게 지금 대부분의 auto-fix 루프가 하는 일이다.
우리 것도 그랬다.

> **리뷰는 여러 번, 수정은 한 번.**

## 1. 환경 — 무엇을 손에 쥐여줄 것인가

**리뷰어에게 리포 접근을 준다. [데이터]**
처음엔 [판단]으로 적었는데 판정이 근거를 줬다. 오탐 4건이 **전부** 파일 밖 사실로
반증됐고, 그 4건이 발견빈도 상위권을 차지한다.
**파일 하나에 갇힌 리뷰어의 가장 자신 있는 지적이 곧 그 리뷰어가 틀린 지적이다.**

**수정자에게 계약을 주는 것은 회귀를 막지 못한다. [데이터]**
2×2로 검정했고 p = 1.0으로 기각됐다. 다만 **거절의 근거는 바뀐다** — 스펙이 있으면 AC를
인용하고, 없으면 코드의 docstring을 인용한다. 주는 게 나쁘진 않다. 다만 그것으로 안전을 사지는
못한다.

**테스트는 오라클로 두되, 무엇을 고정하는지 먼저 확인한다. [데이터]**
AI 수정이 반복해서 같은 테스트를 깬다면 그 테스트가 **프로덕션에서 도달 가능한 상태를 검사하는지**
부터 보라. 우리 경우 4/4로 재현된 "회귀"는 전부 도달 불가능한 상태를 고정한 테스트였고, AI는
아무 잘못도 하지 않았다.

**수정자에게 테스트 실행은 허용하되 테스트 수정은 금지한다. [판단]**
내 실험은 테스트를 숨겼다 — 그래야 "빨개졌다"가 발견이 되니까. 실무에서는 숨길 이유가 없다.
다만 보여주면 테스트가 목표가 되므로, 실행은 열고 편집은 막는 게 맞다.

## 2. 모델 — 무엇을 언제

같은 코드(검증된 19/19)에 대해:

```
                지적 수    루프 5라운드 후      준수율
claude bare       6      감소 없음, 코드 +50%   19/19
claude struct    12      감소 없음, 코드 +24%   19/19
codex  bare       1      3R에 침묵, 코드  +4%   19/19
codex  struct     2      1건까지 감소, 코드 -12% 19/19
```

**[데이터]** 넷 다 계약 준수는 같다. 다른 것은 말의 양과 코드 부피다.

- **발견 폭이 필요하면 claude.** 6~12건을 낸다. 대신 안 멈추고 코드를 늘린다.
- **정제가 필요하면 codex structured.** 유일하게 코드를 **줄이면서** 같은 자리에 도달했다
  (156 → 137줄). 그리고 claude bare가 한 번도 언급 안 한 실패 모드 계열(시계 실패, 프로세스
  제어 예외, wedge)을 찾았다.
- **codex bare의 침묵을 완주 신호로 읽지 마라.** 5라운드 동안 2건만 봤다.

**[판단]** 한 모델을 여러 번 돌리는 것보다 **두 모델을 한 번씩** 돌리는 쪽을 택하겠다. 직접
비교하진 않았지만, 두 모델의 지적 계열이 겹치지 않는 것을 봤다.

## 3. 프롬프트 — structured 우세, 양쪽 모델 다

```
codex:   bare 코드 +4%   →  structured 코드 -12%,  실패모드 계열 추가 발견
claude:  bare 코드 +50%  →  structured 코드 +24%
```

**[데이터]** structured가 코드 부피를 억제하고 더 많은 계열을 본다.

쓴 프롬프트는 코드리뷰의 교과서적 정의(구글 가이드 순서)를 그대로 옮긴 것이다.

```
1 DESIGN         내부 설계가 맞나 (공개 계약은 고정, 범위 밖)
2 FUNCTIONALITY  계약 대비 정확성, 엣지케이스, 에러경로, 재진입
3 COMPLEXITY     과잉 설계, 평탄화 가능한 제어흐름
4 ROBUSTNESS     무한 자원, 새는 예외, 영구 wedge, 조용한 실패
5 NAMING         오해를 부르는 이름, 비자명한 결정의 근거 누락
6 CONSISTENCY    관용, 모듈 내 일관성
```

**[판단]** DESIGN에 *"공개 계약은 고정이고 범위 밖"*을 명시하는 것이 중요하다. 안 쓰면 리뷰어가
API를 바꾸자고 하고, 그건 리뷰어 잘못이 아니라 내가 물어본 것이 된다.

**[데이터]** 그리고 **모든 지적에 채택/거부를 명시**하게 강제하라. 1부는 거절을 선택적으로 뒀고
거부가 0건이었다. 2부는 강제했고 20~26%가 거절됐다. (인과는 미검정 — 가설이다.)

## 4. 횟수와 형태 — 구체적 절차

이 코드 기준이면 나는 이렇게 하겠다.

```
1. 콜을 늘릴 수 있으면 카테고리로 쪼갠다
     Python 대상, 같은 6콜: 동일 프롬프트 고유 19.7  |  카테고리 30.0 (+52%)
     원시 지적은 오히려 21% 적다. 사람이 훑을 게 줄면서 발견은 는다.
     특히 robustness — 일반 리뷰어가 "중요도 순 15건"에서 잘라내는 영역이다.
     ⚠ C 펌웨어에서는 같은 예산에 이득이 없었다 (재현율 43% vs 단일 50%, 실험 8).
       렌즈가 서로 겹치면 팬아웃은 예산만 쓴다. 예산을 3배 쓸 수 있을 때만 이득이다.
     ⚠ 좁은 렌즈는 "밖을 봐라"를 침식한다 — 리포를 열고 없앤 오탐이 하나 돌아왔다.

2. 지적을 묶어 중복을 제거한다
     동일 프롬프트 반복은 같은 걸 3.6번 말한다. 팬아웃은 1.8번.

3. 리뷰어에게 소스 트리 읽기 권한을 준다  ← 오탐 최대 레버
     파일만 주면 오탐 29%, src/ 를 열면 0%. 대신 재현율은 77% → 54%.
     둘 다 원하면 두 조건을 다 돌린다(합집합 13/13).

4. 합의 횟수를 진위의 대리변수로 쓰지 않는다
     파일-스코프에서 오탐의 평균 발견빈도 6.8, 진짜 3.4 — 반-예측적이다.
     리포를 열면 그 상관이 뒤집힌다.
     ⚠ 1번과 충돌한다. 팬아웃이 되살린 오탐은 1/6 이라 합의 필터면 걸렸을 것이다. 미해결.

5. 사람이 훑는다  ← 자동화하지 않는다
     계약 밖 제안, API 변경 요구, 이미 문서화된 의도를 걸러낸다.
     자동 수정자도 20~26%를 거절한다. 사람은 더 걸러야 한다.
     이 단계만 빼고 돌려봤다(실험 9): 수정자가 34%를 거절하며 대신 막았다 —
     작동은 하지만 코드가 3라운드에 +152% 불었다.

6. 한 번에 고친다
     수정자에게 계약과 테스트 읽기 권한을 준다. 편집은 막는다.
     넘긴 이슈의 74~80%가 실제로 사라진다. 이 단계는 작동한다.
     ★ 테스트를 읽히면 수정자가 "이건 테스트를 고쳐야 가능하다"며 스스로 거절한다.
       오라클 범위를 넓히는 것과 같은 효과인데 훨씬 싸다 (실험 9, 빌드실패 4R → 0회).
       단, 고치는 게 아니라 미루는 것이다.

7. 테스트 + 크기 + 복잡도 + churn 을 같이 찍는다
     준수율은 어떤 팔도 구별하지 못한다. 갈라지는 것은 나머지다.
     깨지면 그 테스트가 무엇을 고정하는지부터 본다.
     도달 불가능한 상태면 테스트를 고친다. AI가 아니라.

8. 재리뷰 여부는 라운드 수가 아니라 churn 으로 정한다
     수정이 작다  → 재리뷰의 수확도 작다. 넘어가라.
     수정이 크다  → 그건 재리뷰가 아니라 새 코드에 대한 첫 리뷰다. 해라.
     ⚠ "멈추는 기준은 churn 이 0 에 수렴" 은 조건부다 — 계약이 있는 과제에서만 그랬다.
       계약 없는 C 모듈에서는 churn 이 194→262→395 로 늘기만 했고, 임계에 근처도 못 갔고,
       루프는 결국 "지적 0" 으로 끝났다 (실험 9). 내가 명시적으로 기각한 기준이다.
       계약이 없으면 churn 게이트를 믿지 말고 라운드 상한을 걸어라.
```

## 5. 코드가 좋아졌는지도 재라 — 준수율만 보면 안 보인다

4부 전에는 이 자리에 *"그래서 코드가 좋아졌나에 대해 나는 답이 없다"*라고 써놨었다. 이제 부분적으로
답이 있고, 처방이 하나 늘었다.

**[데이터]** 계약 준수율은 **10개 팔 47라운드 전부 19/19로 완전히 동일**하다. 이 지표로는
어떤 팔도 구별되지 않는다. 그런데 같은 데이터에서:

```
Cognitive Complexity  structured −17%  vs  bare +26%  vs  계약없음 +58%
최악 함수             structured  6.3  vs  bare 10.3  vs  계약없음   15
```

**준수율이 못 보는 것을 복잡도가 본다.** 그러니까 루프를 돌릴 거면 준수율 옆에 크기와 복잡도를
같이 찍어라. 이 둘이 갈라지는 순간이 "리뷰가 이제 코드를 나쁘게 만들고 있다"는 신호다.
그리고 이건 LLM 비용 0이다 — 이미 있는 스냅샷에 AST 한 번 돌리면 된다.

**[데이터]** 그리고 **계약이 비워둔 자리를 찾아라.** 47라운드 동안 움직인 계약 밖 동작은 딱
하나였는데, 그 하나에서 루프는 라운드마다 답을 뒤집었다. 루프가 같은 자리를 두 번 이상 뒤집으면
그건 리뷰어 문제가 아니라 **계약에 구멍이 있다는 신호**다. 고칠 곳은 코드가 아니라 스펙이다.

**[여전히 답 없음]** 설계가 옳은가, 의도를 드러내는가, 이름이 정확한가 — 정전이 리뷰에서 1순위로
놓는 것들은 여기서 하나도 측정되지 않았다. Cognitive Complexity는 이해 가능성의 **검증된
대리변수**이지 이해 가능성 자체가 아니다. 그건 여전히 사람이 읽어야 한다.

# 스펙을 만드는 팀이라면 — 실전 지침

위는 내 개인 레시피다. 아래는 **프로덕션 팀이 월요일에 바로 적용할 수 있는 것**만 추렸다.
연구용 장치(격리 샌드박스, 카나리, 클러스터링)는 전부 뺐다.

## 지금 대부분의 팀이 하는 방식

```
1  PR diff 를 AI 에게 준다                    (파일/diff 만, 리포 접근 없음)
2  리뷰어 3개 돌려서 합의된 것만 통과시킨다
3  auto-fix 를 3라운드 돌린다
4  테스트 green 이면 머지
5  스펙은 있지만 리뷰어/수정자에게는 안 준다
6  모델 하나만 쓴다
```

**이 여섯 중 다섯이 내 데이터에서 역효과이거나 무효였다.**

## 반드시 해라

| | 바꿀 것 | 측정된 효과 | 근거 | 비용 |
|---|---|---|---|---|
| ① | 리뷰어에게 **리포 읽기 권한** | 오탐 29% → **0%** | ★★★ 두 모델 | 설정 한 줄 |
| ② | **루프를 끊어라** — 리뷰 N회 → 사람 → 수정 1회 → 끝 | 커버리지 34%→76%<br>코드 팽창 +88%→**0%** | ★★★ 세 조건 | 없음 |
| ③ | **합의 필터를 꺼라** | 오탐 빈도 6.8 vs 진짜 3.4 | ★★ 판정자=저자 | 없음 |
| ④ | 수정자에게 **스펙 + "공개 표면은 고정"** 한 줄 | 최종 LOC 254 → 202 | ★★ | 한 줄 |
| ⑤ | 수정자에게 **테스트 읽기 허용, 편집 금지** | 빌드 실패 4R → **0** | ★★ n=1.25 | 마운트 하나 |

①이 목록에서 유일하게 **두 모델에서 재현된** 항목이다.

## 하지 마라

```
✗ 라운드 수를 늘려 수렴을 기대하는 것
    claude 는 15라운드를 돌려도 지적이 안 줄어든다. codex 만 준다.

✗ "지적 0" 이나 "churn 0" 을 정지 기준으로 믿는 것
    churn 게이트는 계약이 있는 과제에서만 발화한다.

✗ 테스트 green 을 "코드가 좋아졌다" 로 읽는 것
    10개 팔 47라운드가 전부 19/19 였다. 이 지표는 아무것도 구별하지 못한다.
```

## 스펙을 만들 수 있는 팀만 할 수 있는 것 둘

**⑥ 준수율 옆에 크기·복잡도·churn 을 같이 찍어라.** LLM 비용 0, 스냅샷에 AST 한 번이다.
둘이 갈라지는 순간이 *"리뷰가 이제 코드를 나쁘게 만들고 있다"* 는 신호다.

**⑦ 루프가 같은 자리를 두 번 뒤집으면 코드가 아니라 스펙을 고쳐라.** 47라운드 동안 움직인
계약 밖 동작이 정확히 하나였고 계약이 고정한 104곳은 이동 0이었다. **진동은 공짜로 얻는
스펙 감사다.**

## 카나리의 팀 버전 — 1분짜리

> 월 1회, 리뷰어에게 *"방금 본 파일 말고 **그 호출자 파일의 N행**을 그대로 인용해봐"* 라고
> 시켜라. 못 하면 권한이 안 붙은 것이다.

내 실험에서 이 확인 하나가 **세 번의 오진단**을 잡아냈다. *"설정이 안 붙었다"* 와
*"모델이 원래 그렇다"* 는 밖에서 보면 똑같이 생겼다.

# 콜을 줄이면서 품질을 지키는 법

10회 독립 리뷰가 두 모델치 있으므로 **추정이 아니라 전수 조합**으로 계산했다 — LLM 호출 0회.
참값은 판정된 진짜 10개, 오탐 4개. 미판정 신규는 분자·분모 양쪽에서 뺐다.

| 콜 | 파일만<br>진짜/오탐 | 리포 claude | 리포 codex | **리포 혼합** |
|---|---|---|---|---|
| 1 | 3.40 / **2.70** | 1.40 / 0 | 2.70 / 0 | 2.70 / 0 |
| 2 | 5.04 / **3.62** | 2.09 / 0 | 3.07 / 0 | **3.18** / 0 |
| 3 | 6.11 / **3.90** | 2.54 / 0 | 3.27 / 0 | **3.57** / 0 |
| 4 | 6.93 / **3.98** | 2.90 / 0 | 3.40 / 0 | **3.90** / 0 |
| 6 | 8.20 / **4.00** | 3.43 / 0 | 3.60 / 0 | **4.43** / 0 |

**① 혼합 3콜 = 단일 6콜.** claude 2 + codex 1 이 3.57 인데 claude 단독 6콜이 3.43 이다.
**모델을 섞으면 콜을 절반으로 줄이면서 커버리지가 오히려 높다.** k≥2 에서는 항상 혼합이 이긴다.

**② 리포 조건에서 codex 가 claude 보다 콜당 두 배 가깝게 낫다** (1콜 2.70 vs 1.40).
*"claude 는 말을 아끼고 codex 는 말이 는다"* 가 여기서 값으로 나타난다 — **아끼는 쪽이 놓친다.**

**③ 파일만은 콜당 발견이 가장 많으나**(1콜 3.40) 오탐이 따라오고 **5콜이면 오탐 4개가 전부
나온다**(4.00 포화). 콜을 아낀 만큼 사람 선별 시간으로 낸다 — **비용을 없앤 게 아니라 옮긴 것.**

## 예산이 빠듯하면

```
2콜   claude 1 + codex 1     진짜 3.18개 · 오탐 0
      같은 2콜을 파일만 단일에 쓰면 진짜 5.04개를 보지만 오탐 3.62개를 사람이 걸러야 하고,
      그건 가장 그럴듯한 것들이다

4콜   claude 2 + codex 2     진짜 3.90개 — 단일 10콜(4.00)에 근접
      ★ 콜 60% 절감하고 커버리지를 유지하는 지점
```

⚠️ 이 표의 분모는 **대조군이 찾은 진짜 10개**다. 리포 조건이 새로 찾은 결함(claude 3 ·
codex 5)은 미판정이라 빠져 있는데, **판정되면 리포 조건의 숫자만 올라간다.** 즉 이 표는
리포 접근에 **불리한 쪽으로 치우쳐 있다.**

# 아직 모르는 것

- **"계약"은 두 가지를 한 덩어리로 준 것이다 — 분리한 적이 없다.** 2×2 에서 계약 있음/없음을
  가른 프롬프트 diff 를 보면 계약 팔에만 있는 것이 둘이다: ① **SPEC 문서**(19 AC) 자체,
  ② **범위 고정 문장** — *"공개 계약은 FIXED 다. 생성자 시그니처·메서드/프로퍼티 이름·문서화된
  동작은 스펙 그대로 유지해야 한다. 그것을 바꾸라는 지적은 범위 밖이니 거절하고 그렇게 말해라."*
  두 팔 **모두**에 있던 것은 따로 있다 — *"지적이 묻지 않은 코드를 다시 쓰지 마라, 리포맷·리네임
  금지, 틀린 지적은 거절해라."* 즉 **"수정 범위 제한"은 상수**였고 갈린 것은 **"무엇이 계약인지
  아는가"** 다. 세 층으로 쓰면:

  ```
  A  손대지 마라 (리팩터·리네임·리포맷 금지)      항상 상수 — 측정 안 됨
  B  공개 표면이 계약이고 고정이다                계약 팔에만
  C  그 계약의 내용 (19 AC 문서)                 계약 팔에만
  ```

  **B 와 C 가 한 번도 분리되지 않았다.** 그래서 "계약이 120 지점 중 104 를 고정했다"는 C 의
  효과처럼 읽히지만 실제로는 **B+C 묶음**의 효과다. 리뷰어 쪽 structured 프롬프트의
  *"공개 계약은 고정, 범위 밖"* 한 줄도 6개 카테고리와 묶여 있어 같은 문제가 있다.
  **"범위만 정해줘도 진동이 줄어드는가"** 를 검정하려면 *B 는 주고 C 는 안 주는 셀*
  (= "공개 표면은 고정이다, 다만 그 내용은 코드에서 읽어라")이 필요한데, 그 셀이 없다.
- **처방을 전부 켠 조건의 n 이 1.25 루프다.** 4라운드 전부 GREEN 은 고무적이지만 한 루프가
  중간에 죽었고, 가장 비싼 단계(사람 선별)를 뺐다. **상한이 아니라 하한을 잰 것이다.**
- **팬아웃이 예산 효과인지 구조 효과인지 갈렸다.** Python 에서는 같은 예산에 +52%, C 펌웨어에서는
  같은 예산에 이득 없음. 축의 분리도를 먼저 재야 한다는 뜻인데 그 재는 법을 아직 모른다.
- **"합의를 믿지 마라"와 "카테고리로 쪼개라"가 충돌한다.** 팬아웃이 되살린 오탐은 1/6 이라
  합의 필터면 걸렸다. 두 규칙을 어떻게 합칠지 답이 없다.
- **1부와 2부가 정반대인 이유를 절반만 밝혔다.** 2×2로 "수정자가 계약을 쥐었는가"는 기각했고
  (p = 1.0), 남은 설명은 "테스트가 도달 불가능한 상태를 고정하고 있었다"이다. 이건 C 사례를
  직접 확인해서 아는 것이지 실험으로 분리한 것은 아니다. **외부 호출자 유무**와 **언어·크기**는
  여전히 분리 못 했다 — 분리하려면 외부 호출자가 있는 Python 모듈이라는 네 번째 셀이 필요하다.
- **계약 밖 동작이 한 가지만 움직였다는 결과는 양날이다.** *"리뷰 루프가 안전하다"*로도 읽히고,
  *"이 과제의 계약이 촘촘해서 움직일 자리가 없었다"*로도 읽힌다. 156줄을 19개 AC로 덮는 과제는
  실무 평균보다 계약 밀도가 확실히 높다. 계약이 성긴 코드에서 같은 숫자가 나올 거라는 근거는 없다.
- **복잡도 결과는 프롬프트 효과지 "리뷰 효과"가 아니다.** structured가 줄이고 bare가 늘렸다.
  "AI 리뷰가 코드를 단순하게 만든다"는 문장은 이 데이터로 쓸 수 없다.
- **개별 지적의 참/거짓은 부분적으로만 판정했다.** 팬아웃 39건은 판정했으나(REAL 31% / WRONG 0)
  판정자가 저자 본인이고 p = 0.236이다. 1·2부의 지적은 여전히 미판정.
- ~~개별 지적의 참/거짓은 판정하지 않았다.~~ 수정 후 테스트가 깨져도 그건 *지적이 틀렸다*가
  아니라 *수정자가 계약을 손상했다*이다.
- **격리는 리포에 대해서만 완전했다.** 실험이 끝난 뒤 감사해봤다. CLAUDE.md·프로젝트 규칙·
  AGENTS.md는 들어가지 않았고(카나리를 심는 positive control로 확인), 세션 전사 190개에
  도구 호출은 0건이었다. 그런데 **도구가 전부 막혀 있진 않았다** — `Skill`·`ToolSearch`·
  `Workflow`는 차단 목록에 없었고, CLI 내장 스킬(`code-review`·`security-review` 포함)이
  사용 가능한 상태였다. 더 중요한 건 **codex는 네트워크 도구를 끌 방법이 아예 없다는 것**이다.
  claude 쪽은 WebFetch/WebSearch를 껐으니 **네트워크 접근이 모델 간 비대칭**이다. 실측으로는
  아무도 쓰지 않았지만, "능력이 대칭이었다"고는 말할 수 없다.
- 과제 하나, 모델 둘. 사례연구다.
- 실제 AI 리뷰 도구들은 대부분 심각도-우선 프롬프트를 쓴다. 이 실험의 구조화 팔은 교과서
  정의(설계-우선)였다.

# 내 결론이 뒤집힌 횟수

기록해둔다. 데이터가 들어올 때마다 이전 결론이 깎였고, 방향은 **항상 덜 극적인 쪽**이었다.

| 처음 쓴 것 | 실제 |
|---|---|
| "라운드2 지적의 83%가 수정 때문" | 우연 수준이 59% → 실질 1.4배 |
| "귀속 지표는 완전히 null" | fix가 클 때만 무력 |
| "루프는 자기교정한다" | 루프 2가 반증 |
| "주석 제거하면 5배" | 반복하니 2.8배 |
| **"AI 수정이 버그를 만든다, 4/4 재현"** | **절반 이상이 도달 불가능한 상태를 고정한 테스트** |
| **"정답 코드에도 리뷰는 끝나지 않는다"** | **claude 한정. codex는 두 팔 다 감소, bare는 침묵** |
| **"codex가 멈춘 것은 우월하다"** | **침묵한 팔이 5라운드 동안 2건만 봄 — 덜 본 것일 수도** |
| **"수정자에게 계약을 주면 회귀가 막힌다"** | **2×2 로 기각. p = 1.0. 원인은 테스트의 성격이었다** |
| "189건이 반영됐으니 계약 밖은 당연히 흔들렸을 것" | 47라운드에서 움직인 관측 동작은 **딱 하나** |
| "덜 고치는 쪽이 안전하다" | 3배 이상 갈아엎은 팔이 더 **작고 단순하게** 끝났다 |
| "여러 리뷰어가 반복 지적하니 진짜겠지" | **오탐이 더 자주 발견된다** (6.8 vs 3.4회) |
| "고친 뒤 다시 리뷰할 필요 없다" | 신규율이 귀무분포 최댓값의 **2배 이상** |
| "팬아웃은 뭐라도 말해야 해서 잡음이 는다" | **정반대.** 같은 6콜에 고유 +52%, 원시 −21% |
| "한 번에 크게 고치는 게 낫다" | 복잡도는 **더 나빠진다** (cog 29 vs 22) |
| "처방 9개를 전부 켠 조건을 잴 수 있다" | 절반이 루프 전용이고 하나는 이미 상수였다 |
| **"churn 이 0 에 수렴하면 멈춘다"** | **계약 있을 때만. 없으면 194→262→395 로 늘기만** |
| **"codex 는 리포 접근을 못 돌린다 (설치 결함)"** | **내가 스크래치를 /tmp 에 뒀을 뿐. 옮기니 오탐 0/4 로 재현** |

뒤의 다섯 줄은 전부 동료의 질문 하나로 뒤집혔다. *"정말 버그인가?"* *"코덱스로도 하는 건가?"*
*"추가 실험으로 밝힐 수 있나?"* *"코드가 좋아졌냐를 판단할 지표는 없어?"*
*"한 번에 고친 뒤 다시 리뷰할 필요는 없을까, 고친 부분이 꽤 있다면?"*

공교롭게도 이 글의 주제 그 자체다. 이 실험의 **계획서**도 리뷰를 세 번 받았는데, 2·3라운드 지적의
절반 이상이 **내가 직전 라운드에 한 수정 때문에** 생긴 것이었다.
