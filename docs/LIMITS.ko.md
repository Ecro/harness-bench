# 한계 — 이 벤치로 주장할 수 없는 것

[English](LIMITS.md)

**모델 순위표가 아니다.** 이것은 *하네스 설계*의 효과를 잰다. "어느 모델이 더 똑똑한가" 가
아니라 "이 모델을 어떻게 운용해야 하는가" 다. 순위로 인용되면 오독이다.

---

## 1. 근거 등급은 결과의 일부다

이 계열의 작업에서 **한 번 이상 재현된 문장은 셋뿐이다.**

```
***  리뷰 반복과 수정 루프는 다른 활동이다
***  단일 파일 범위에서는 가장 자신 있게 보고된 지적이 가장 의심스럽다
***  계약 준수율은 아무것도 판별하지 못한다 — 모든 팔이 유지한다
```

나머지는 한 번씩 관측된 것이다. 모든 처방 줄에 등급이 붙는 이유이고, 등급 없는 규칙이 아예
렌더되지 않는 이유다.

## 2. 모델 비교는 tier-1 에 한한다

모델 비교는 계약이 오라클이고 사람이 판정하지 않는 tier-1 과제 위에 선다. tier-2 케이스
스터디는 무엇이 진짜 결함인지에 대한 사람의 판단을 담고 있으며, *"우리가 이렇게 봤다"* 의
기록이지 *"당신도 같은 숫자를 얻는다"* 가 아니다.

## 3. 재현율의 분모는 낙관적이다

재현율의 분모는 **알려진** 결함의 집합이지 존재하는 결함의 집합이 아니다. 아무도 못 찾은
것은 분자에도 분모에도 없고, 새 조건이 새로운 것을 찾을 때마다 분모가 늘어난다. 따라서 모든
커버리지 수치는 위쪽으로 치우쳐 있다.

## 4. 입을 막을 수 없는 모델

어떤 CLI 에는 도구를 끄는 플래그가 없다. 읽기 전용 샌드박스 정책은 읽기를 **허용**하는
것이지 능력을 제거하는 것이 아니다.

> 도구를 끌 수 있는 모델과 없는 모델을 같은 표에 놓는 것 자체가 교란이다.

현재의 처리는 그것을 **선언**하고(`tools_blockable: false`) 그 행에 낙인을 찍는 것이다.
해결이 아니라 공시다. 파일시스템 격리는 네임스페이스로 여전히 성립하지만, 능력의 대칭은
성립하지 않는다.

## 5. 과제 둘, 언어 하나

tier-1 은 Python 두 과제다. 이 결과를 다른 언어나 도메인으로 옮길 근거는 없다 — 실제로 한
결과는 대상을 바꾸자 뒤집혔다(카테고리 팬아웃은 Python 에서 동일 예산에 고유 발견 +52% 였고,
렌즈가 서로 겹치는 C 펌웨어에서는 이득이 없었다).

## 6. 작은 n

대부분의 결과가 3루프 위에 선다. 날카로운 대비는 n 이 늘면 줄어든다. 비율이 문턱 근처에
몰리는 특성은 **3루프 이상이어야 판정되며**, 프레임워크는 그 미만에서 판정을 거부한다.

## 7. 자동 실행은 하한을 잰다

권장 절차의 한 단계는 *"사람이 지적을 훑는다"* 이고, 자동 실행은 그것을 뺀다. 그것 없이 나온
수치는 상한이 아니라 **바닥**이다.

## 8. 실행 시점이 결과의 일부다

모델은 예고 없이 바뀌고, 별칭은 배치 도중 다른 백엔드로 재지정될 수 있다. 결과에는 **해석된**
모델 id 와 프롬프트 SHA-256 이 기록된다. 그럼에도 6개월 전 수치와 오늘 수치의 차이가 모델
변화인지 조건 변화인지를 결과 파일만으로 항상 가를 수는 없다. 재현 불가가 된 행은 `stale` 로
표시하고 삭제하지 않는다.

## 이 벤치가 답하지 않는 질문

- 설계가 옳은가, 의도를 드러내는가, 이름이 정확한가 — 정전(正典)이 코드리뷰에서 1순위로 놓는
  것들은 **여기서 하나도 측정되지 않는다.** Cognitive Complexity 는 이해 노력의 검증된
  대리변수이지 이해 그 자체가 아니다.
- 어느 모델이 더 나은 프로그래머인가.
- 이 결과가 당신의 코드베이스에서도 성립하는가.
