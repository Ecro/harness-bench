# 그래서 리뷰를 어떻게 해야 하는가

[English](PRESCRIPTION.md) · 장문 서사: [`STUDY-ko.md`](STUDY-ko.md)

측정 결과를 바탕으로 정리한 실전 레시피다. **AI에게 코드 리뷰를 시키는 파이프라인을 만들거나
고치는 사람**을 위한 문서이고, 각 항목에는 그 권고를 뒷받침하는 근거의 강도를 함께 적었다.

자세한 수치는 [`FINDINGS.ko.md`](FINDINGS.ko.md), 이 결과로 주장할 수 없는 범위는
[`../LIMITS.ko.md`](../LIMITS.ko.md)에서 확인할 수 있다.

각 권고 끝에는 **근거의 강도**가 붙는다. 같은 "권고"라도 무엇에 기대고 있는지가 다르다.

```text
[재현됨]     서로 다른 모델 또는 서로 다른 조건에서 같은 결과가 나왔다
[1회 측정]   한 조건에서 한 번 측정됐다. 아직 재현되지 않았다
[판단]       데이터가 직접 뒷받침하지는 않는다. 관측에 근거한 판단이다
```

`bench prescribe` 가 내는 기계 출력과 원장에서는 같은 등급이 각각 `***` · `**` · `*` 로
찍힌다. 등급 없는 규칙은 아예 렌더되지 않는다 — 등급이 없으면 의견이 조언으로 세탁된다.

## 이 문서의 용어

이 연구는 리뷰를 **두 개의 역할**로 나눠서 측정했다. 이 구분이 문서 전체의 뼈대다.

```text
리뷰어(reviewer)   코드를 읽고 문제를 보고한다. 코드는 건드리지 않는다
수정자(fixer)      그 보고를 받아 실제로 코드를 고친다. 거절할 수도 있다
```

| 용어 | 뜻 |
|---|---|
| **지적**(finding) | 리뷰어가 한 건으로 보고한 항목. 진짜인지 아닌지는 별개다 |
| **오탐**(false positive) | 결함이라고 보고됐지만 실제로는 결함이 아닌 것 |
| **고유 지적 / 원시 지적** | 같은 문제를 가리키는 지적을 하나로 묶은 개수 / 묶기 전의 총 개수 |
| **콜**(call) | 모델 호출 1회. 비용의 단위다 |
| **라운드 / 루프** | 리뷰→수정 1회가 한 라운드, 그 라운드를 여러 번 반복한 것이 한 루프 |
| **계약**(contract) | 그 코드가 지켜야 할 동작을 못박아 둔 명세와 그것을 검사하는 테스트 |
| **준수율** | 그 계약을 지키고 있는 비율. `19/19`, `23/23` 은 조건과 테스트를 전부 통과했다는 뜻 |
| **공개 표면** | 다른 코드가 의존하는 부분 — 함수 이름, 시그니처, 문서화된 동작 |
| **파일만 / 리포 접근** | 리뷰어에게 대상 파일 하나만 준 조건 / 소스 트리를 읽기 전용으로 열어준 조건 |
| **혼합** | 한 모델을 반복하는 대신 서로 다른 두 모델에 호출을 나눠 준 조건 |
| **정밀도 / 재현율** | 보고한 것 중 진짜의 비율 / 실제 존재하는 결함 중 찾아낸 비율 |
| **churn** | 한 라운드에서 추가·삭제된 줄 수. *얼마나 손댔는가*이지 품질이 아니다 |
| **거절률** | 수정자에게 넘긴 지적 중, 수정자가 근거를 밝히고 고치지 않기로 한 비율 |
| **fan-out** | 한 리뷰어에게 전부 맡기는 대신 영역별 전문 리뷰어로 나눠 돌리는 방식 |
| **렌즈**(lens) | 그때 한 리뷰어에게 지정해 준 관점. 예: "동시성만 봐라" |

## 가장 중요한 원칙

| | 이득 | 비용 |
|---|---|---|
| **리뷰만 반복** | 진짜 결함 커버리지 34% → 61% → 76% | 없음. 코드가 바뀌지 않는다 |
| **리뷰→수정 루프 반복** | 이미 만점이던 계약 준수율은 그대로 | 코드 +24% ~ +152% |

커버리지는 *존재하는 진짜 결함 중 몇 퍼센트를 찾았는가*이고, 위 숫자는 리뷰를 1회 · 3회 ·
5회로 늘렸을 때의 값이다.

> ### 리뷰는 여러 번, 수정은 한 번. `[재현됨]`

발견의 이득은 리뷰 쪽에서 나오고, 코드 변경의 위험은 수정 쪽에서 생긴다.
둘을 매번 번갈아 수행하는 하네스 — 즉 모델을 감싸는 루프 구조 — 는 발견 이득보다 수정 비용을
빠르게 키울 수 있다.

## 절차

```text
1  리뷰어에게 소스 트리 읽기 권한을 준다              [재현됨]
     대상 파일만 보여줬을 때는 고유 결함의 29%가 오탐이었고,
     같은 리뷰어에게 리포지토리를 읽게 하자 0%가 됐다. 두 모델 모두 같았다.
     대신 재현율은 77% → 54%로 떨어졌다. 확인할 수 있게 되자 리뷰어가
     "실제로는 거의 도달하지 않는다"고 판단하고 말을 아꼈기 때문이다.
     둘 다 놓치고 싶지 않다면 두 조건을 모두 돌리고 결과를 합친다
     (그렇게 20콜을 쓰면 판정된 결함 13개를 전부 찾았다).

2  여유가 있다면 같은 리뷰를 반복하기보다 카테고리로 나눈다   [1회 측정]
     같은 6콜에서, 같은 프롬프트를 여섯 번 반복하면 고유 지적이 19.7개였고
     여섯 영역(설계·기능·복잡도·견고성·이름·스타일)으로 나누면 30.0개(+52%)였다.
     읽어야 할 원시 지적은 오히려 21% 적었다. 같은 말을 덜 반복하기 때문이다.
     ⚠ 다만 리뷰 영역이 서로 겹치는 과제에서는 이득이 없었다.
       카테고리가 실제로 분리되는지 먼저 확인해야 한다.
     ⚠ 좁은 렌즈는 리포 접근의 장점을 일부 상쇄할 수 있다.
       "모듈 내부 상태만 보라"는 조건에서, 리포 접근으로 사라졌던 오탐 하나가 다시 나타났다.

3  여러 리뷰어의 합의를 진위 판단 기준으로 쓰지 않는다     [재현됨]
     파일만 본 조건에서 오탐은 10회 중 평균 6.8회 보고됐고,
     진짜 결함은 3.4회였다. 자주 지적된 쪽이 오히려 오탐이었다는 뜻이다.
     리뷰어들이 모두 같은 정보를 못 봤기 때문에 같은 오답에 모인 것이다.
     리포를 열면 이 관계가 뒤집힌다.
     ⚠ 한 조건에서는 2번과 충돌했다. 두 규칙을 함께 쓸 때의 필터 기준은 아직 없다.

4  사람이 한 번 선별한다 — 자동화하지 않는다                        [1회 측정]
     판정한 지적의 69%는 이름·주석·구조에 관한 것이었다. 틀린 말은 아니지만
     결함도 아니다. 이런 항목까지 모두 수정자에게 넘길 필요는 없다.
     사람 선별을 빼도 파이프라인은 돌았지만, 수정자가 34%를 대신 거절했고
     코드는 3라운드 만에 152% 커졌다.

5  지적을 모아서 한 번에 수정한다. 계약과 테스트 읽기 권한도 함께 준다  [1회 측정]
     넘긴 지적의 74~80%가 다음 리뷰에서 실제로 사라졌다. 모아서 한 번에 고치는 방식은
     그 자체로는 잘 작동한다.
     테스트를 읽을 수 있고 수정할 수는 없게 하자, 수정자가 모듈 밖 변경을 시도하는 대신
     거절하기 시작했다. 그 결과 한 루프에서 반복되던 빌드 실패가 0이 됐다.
     다만 이것은 해결이 아니라 범위 밖으로 미룬 것이다.

6  테스트뿐 아니라 크기·복잡도·churn을 함께 기록한다            [재현됨]
     계약 준수율은 10개 조건 47라운드에서 전부 19/19였고,
     벤치 자체 실행에서도 54라운드 모두 23/23이었다. 즉 테스트 통과 여부만으로는
     어떤 방식이 더 나은지 구분할 수 없었다.
     반면 복잡도는 크게 갈렸다 — 구조화된 리뷰 프롬프트를 쓴 조건은 −17%,
     수정자에게 계약을 주지 않은 조건은 +58%였다.
     비용은 코드를 한 번 파싱하는 것뿐이다. 추가 모델 호출은 필요 없다.

7  재리뷰 여부는 라운드 수보다 수정량(churn)으로 판단한다     [1회 측정]
     수정이 작으면 다음 리뷰의 수확도 작았다.
     수정이 크면 새로 작성된 코드가 많으므로 다시 리뷰할 가치가 있다.
     실제로 신규 지적률은 수정 churn과 함께 움직였다(상관계수 r = 0.837).
     ⚠ "churn이 0으로 수렴하면 멈춘다"는 보편적인 규칙이 아니었다.
       계약이 있는 과제에서는 성립했지만, 없는 과제에서는
       194 → 262 → 395줄로 계속 증가했다.
       계약이 없다면 라운드 상한을 따로 두는 편이 낫다.

8  루프가 같은 결정을 반복해서 뒤집으면 스펙을 확인한다    [1회 측정]
     47라운드 동안 실제로 바뀐 동작은 정확히 하나였고,
     그것은 계약이 정의하지 않은 유일한 영역이었다.
     같은 결정을 두 번 이상 뒤집는다면 코드보다 스펙이 비어 있는지 먼저 봐야 한다.

9  스펙이 없어도 "공개 표면은 고정"이라는 범위는 명시한다   [1회 측정]
     다른 코드가 의존하는 부분은 바꾸지 말라는 이 한 줄만으로
     최종 코드 줄 수는 7%, 누적 churn은 30% 줄었다.
     ⚠ 대신 거절률은 26% → 50%로 늘었다.
       무엇이 고정돼 있는지 확인할 문서가 없으면 애매한 변경을 보수적으로 거절하기 때문이다.
       그 거절의 절반이 실제 손실이었는지는 측정하지 않았다.

10 같은 모델을 두 번 돌리기보다 서로 다른 모델을 한 번씩 돌린다   [재현됨]
     두 모델 모두 같은 오탐 4개를 제거했지만, 찾아낸 진짜 결함은 달랐다
     (각각 10개 중 4개, 합집합은 5개).
     혼합 3콜이 단일 모델 6콜(리포 A)보다 더 많은 진짜 결함을 찾았다.
```

## 예산

기존 실행의 모든 부분집합을 전수 계산한 결과다. 추가 호출은 없었다.
판정이 끝난 진짜 결함 10개를 기준으로 한 평균값이다(**진짜 발견 / 오탐 발견**).

| 콜 | 파일만 | 리포 A | 리포 B | **혼합** |
|---|---|---|---|---|
| 2 | 5.04 / **3.62** | 2.09 / 0 | 3.07 / 0 | **3.18** / 0 |
| 3 | 6.11 / **3.90** | 2.54 / 0 | 3.27 / 0 | **3.57** / 0 |
| 4 | 6.93 / **3.98** | 2.90 / 0 | 3.40 / 0 | **3.90** / 0 |
| 6 | 8.20 / **4.00** | 3.43 / 0 | 3.60 / 0 | **4.43** / 0 |

리포 A와 리포 B는 리포 접근을 준 서로 다른 회사의 두 모델이다.

**2콜:** 모델별로 한 번씩 돌린다. 평균 진짜 3.18개, 오탐 0개다.
같은 2콜을 파일-only 조건의 한 모델에 쓰면 진짜 5.04개를 찾지만 오탐 3.62개도 함께 나온다.
그리고 그 오탐들이 오히려 가장 그럴듯해 보이는 지적들이었다.

**4콜:** 모델별 두 번씩 돌리면 3.90개를 찾는다.
단일 모델 10콜의 4.00개에 근접하면서 호출 수는 60% 적다.

파일만 보면 콜당 더 많은 결함을 찾는다.
다만 절약한 비용이 사라지는 것은 아니다. 오탐을 걸러낼 사람의 선별 비용으로 옮겨갈 뿐이다.

## 무한 루프를 벗어나는 법

리뷰→수정을 언제까지 반복할 것인가. 정지 기준 후보 네 가지 중 세 가지는 일반적인 기준으로
쓰기 어려웠다.

```text
churn → 0        계약이 있는 과제에서만 성립. 다른 조건에서는 계속 증가했다.
지적 0           실제로 한 루프를 끝냈지만, 덜 본 결과일 수도 있다.
라운드 상한       수렴이 아니라 강제 종료다.
루프를 안 돈다    ← 가장 단순한 대안
```

"지적 0"이 위험한 이유는 이렇다. 한 모델은 3라운드부터 아무것도 보고하지 않았는데, 같은
코드에 구조화된 프롬프트를 준 조건에서는 그 뒤로도 다른 실패 모드가 계속 나왔다. 침묵한 쪽이
다 본 것이 아니었다.

또 하나의 현실적인 정지 요인이 있다. 파일이 커지면 리뷰 자체가 느려진다.
한 실험에서는 900줄짜리 파일의 4라운드 리뷰가 15분 제한을 넘겼다.
오래 돌린 루프는 수렴이 아니라 타임아웃으로 끝날 수 있다.

## 스펙을 만드는 팀이라면

위 절차에 더해 두 가지를 활용할 수 있다.

**준수율 옆에 크기·복잡도·churn을 같이 기록한다.**
추가 모델 호출 없이 코드를 한 번 파싱하는 것만으로 측정할 수 있다.
테스트는 계속 통과하는데 코드 크기와 복잡도가 증가한다면,
그 시점부터는 리뷰가 실제로 무엇을 개선하고 있는지 다시 확인해야 한다.

**반복되는 진동을 스펙 감사로 활용한다.**
루프가 같은 결정을 계속 뒤집는 지점은 계약이 정의하지 않은 영역일 가능성이 높다.
코드를 계속 수정하기보다 스펙에서 의도를 먼저 고정하는 편이 낫다.

### 카나리의 1분짜리 팀 버전

> **카나리**(canary) — 측정을 시작하기 전에 *장치가 실제로 붙어 있는지* 확인하는 프로브.
> 이 벤치의 카나리는 두 방향을 함께 본다 — 보여야 할 것이 보이는가(POS), 안 보여야 할 것이
> 정말 안 보이는가(NEG). POS 가 실패하면 격리가 성공한 것이 아니라 **프로브가 고장난 것**이고,
> 그 상태에서 모은 수치는 무효다. 자세히는 [`METHODS.ko.md`](METHODS.ko.md).

연구용 장치까지 만들 필요는 없다. 1번 권고(리포 읽기 권한)가 실제로 적용됐는지만 확인하면 된다.

*"설정이 적용되지 않았다"* 와 *"모델이 원래 그렇게 동작한다"* 는 결과만 보면 구분하기 어렵다.
이 간단한 확인으로 둘을 분리할 수 있다.
