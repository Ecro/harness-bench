# review-convergence — 설계와 결과

[English](README.md)

이 실험이 던지는 질문: **AI 코드리뷰를 반복하면 수렴하는가, 그리고 그 루프의 비용은 얼마인가?**

이 문서는 실험의 설계와 벤치마크 자체의 실행 결과를 담는다.
연구 전체에서 나온 측정값은 [`FINDINGS.ko.md`](FINDINGS.ko.md), 계측기의 검증 절차는
[`METHODS.ko.md`](METHODS.ko.md)에 있다.

---

## 1. 설계

### 계약이 곧 오라클

오라클은 어떤 결과가 옳은지 그른지를 판정하는 기준을 말한다.
이 실험에서는 각 과제가 명세, 그 명세에서 파생한 **동결** 인수 스위트, 그리고 알려진 정답
구현이 있는 경우 참조 구현을 함께 싣는다. 동결이란 구현이 존재하기 전에 확정하고 그 뒤로는
고치지 않는다는 뜻이다.

**스위트가 오라클이므로 사람의 판정이 필요 없다.** 그래서 새 모델이 나왔을 때 사람 손을 거치지
않고 그대로 다시 돌릴 수 있다.

### tier-1 과제

tier-1은 계약과 고정 테스트만으로 판정이 끝나는, 누구나 재현할 수 있는 과제를 가리킨다.

| 과제 | 계약 | 참조 | 비고 |
|---|---|---|---|
| `retry_policy` | 인수 조건 19개 | 있음, 128줄 | 지수 백오프 + full jitter + 서킷 브레이커 |
| `ttl_cache` | 인수 조건 8개 | **없음, 의도적** | 계약이 침묵하는 자리에서 모델이 무엇을 고르는가 |

인수 조건은 명세가 보장하는 동작을 검증 가능한 문장 하나로 쪼갠 것이다.
과제는 표준 라이브러리와 `pytest` 만 쓰고 별도 툴체인이 필요 없다.

### 오라클은 쓰기 전에 검증된다

```text
retry_policy    참조 통과                    23/23
                import 실패 시 바닥           0 passed
                보증 1개 제거 시 적발         3개 테스트가 잡는다
ttl_cache       참조 통과                    SKIP (의도적으로 참조 없음)
                import 실패 시 바닥           0 passed
```

보증을 하나 지웠는데도 초록인 스위트는 **그 보증을 재고 있지 않다.**
`oracle.verify()` 가 통과하기 전에는 그 과제에서 나온 어떤 수치도 인용할 수 없고, CI 가 매
푸시마다 이 검사를 돌린다.

### 측정 한 벌의 비용

```text
변동폭    n_spread 콜                검증된 v0 를 반복 리뷰한다. 코드는 바뀌지 않는다
루프      n_loops × n_rounds × 2     리뷰 → 수정 → 오라클
파생      0 콜                       LOC · 준수 · malformed · 거절률
```

`n_spread` 는 같은 코드를 몇 번 리뷰할지, `n_rounds` 는 한 루프에서 리뷰→수정을 몇 번 반복할지,
`n_loops` 는 그 루프 전체를 몇 번 되풀이할지를 정한다. 마지막 줄의 값들은 이미 받은 응답에서
계산하므로 추가 호출이 들지 않는다 — `malformed` 는 구조화 출력을 지시했는데도 파싱되지 않은
응답의 비율이다.

기본값인 변동폭 5회 + 3루프 × 5라운드이면 **모델당 35콜**이다. 새 모델을 표에 얹는 값이 그
정도여야 한다. 더 비싸면 아무도 얹지 않는다.

## 2. 결과

2026-08-21 측정. 과제는 `retry_policy`, 두 모델을 각각 3루프씩 돌렸다.

### 헤드라인

**리뷰어는 이미 정답인 코드에도 지적을 낸다. 그리고 그 루프는 그러는 동안 계약을 한 번도
깨지 않는다.**

```text
v0 는 인수 테스트 23/23 을 통과한다.

claude   독립 리뷰 5회 전부 12~14건 보고
codex    독립 리뷰 5회 전부  3~5건 보고

루프 30라운드(claude) + 24라운드(codex): 계약 준수가 매 라운드 23/23.
```

따라서 **준수율은 판별력이 없다.** 조건을 가르는 것은 나머지 전부다.

### 원장

| 모델 | 판본 | 콜 | 비용 | loop_decay | churn_dries | churn_ratio | 거절률 | loc_direction | 도구 차단 |
|---|---|---|---|---|---|---|---|---|---|
| claude | claude-opus-5 | 30 | $15.74 | −1.25 | False | 0.688 | 0.209 | **1.258×** | 가능 |
| codex | gpt-5.6-sol | 24 | 미상 | −0.25 | — | 0.394 | 0.273 | **0.906×** | **불가** |

각 열의 뜻은 다음과 같다.

| 열 | 뜻 |
|---|---|
| **loop_decay** | 라운드가 갈수록 지적 수가 줄어드는 기울기. −1.25 는 라운드마다 평균 1.25건씩 줄었다는 뜻 |
| **churn_dries** | 후반 절반의 평균 변경량이 전반 절반의 0.7배 아래로 떨어졌는가(참/거짓) |
| **churn_ratio** | 그 비율 자체. 이분법이 문턱에 걸릴 때를 위해 연속값을 함께 기록한다 |
| **거절률** | 수정자에게 넘긴 지적 중 수정자가 근거를 밝히고 고치지 않기로 한 비율 |
| **loc_direction** | 마지막 라운드의 코드 줄 수 ÷ 시작 코드. 1보다 크면 불었고 작으면 줄었다 |
| **도구 차단** | 그 CLI 에서 모델의 도구 사용을 실제로 끌 수 있는가. 끌 수 없는 모델은 비교의 교란 요인이다 |

`churn` 은 한 라운드에서 추가·삭제된 줄 수, 즉 얼마나 손댔는가이지 품질 지표가 아니다.

### 결과 1 — 루프는 코드를 늘리거나 줄이고, 그 방향은 모델의 성질이다

```text
claude   1.258×    라운드마다 코드가 는다
codex    0.906×    지적을 반영하면서 코드가 준다
```

이 벤치에서 가장 강한 교차모델 결과다. 두 방향이 각각 독립적으로 측정됐고, 다른 과제군에서
관측된 같은 분기와도 일치한다. **루프를 얼마나 오래 돌려도 안전한지를 이것이 결정한다.**

### 결과 2 — churn 수렴은 모든 모델에서 쓸 수 있는 정지 기준이 아니다

*"churn 이 0 으로 떨어지니 거기서 멈추면 된다"* 는 직관은 두 모델 어디에서도 성립하지
않았고, 성립하지 않은 이유가 서로 달랐다.

```text
claude   L1 [90, 100, 107,  65, 51]   ratio 0.611
         L2 [101, 82, 101, 101, 33]   ratio 0.732
         L3 [106, 69,  82,  51, 75]   ratio 0.720
         판정: 수렴하지 않음 (1:2 갈림)

codex    L1 [54, 13]                  2점 — 판정하기에 너무 짧다
         L2 [22, 20, 3, 15, 5]        ratio 0.476
         L3 [49, 18, 18, 3]           ratio 0.313
         판정: 측정 불가 (3루프 중 2개만 사용 가능)
```

여기서 두 가지가 따라 나온다.

**claude 의 세 비율은 0.611~0.732 로 문턱 0.7 을 걸치고 있다.** 루프 하나만 뽑으면 어느 쪽으로도
떨어질 수 있다. 그래서 이 특성은 **3루프 이상이어야 판정하고**, 참/거짓과 함께 연속값
`churn_ratio` 를 같이 읽어야 한다.

**codex 는 계열이 충분히 길어지기 전에 루프가 끝난다.** 정확한 서술은 *"codex 는 빨리 마른다"*
가 아니라 *"codex 는 이것을 측정할 만큼 오래 돌지 않는다"* 다 — 루프가 3라운드와 5라운드에
지적 0 에 도달했다. 서로 다른 서술이고, 후자가 맞다.

### 결과 3 — 수정자는 넘겨받은 것의 1/5~1/4 를 거절한다

```text
claude   0.209   (32 / 153)
codex    0.273   ( 9 /  33)
```

거절할 때는 계약을 인용한다. 수정자는 리뷰 지적이 실제 코드 변경이 되기 전의 마지막 관문이고,
고무도장이 아니다.

### 결과 4 — 지적은 천천히 줄고, 한 모델에서는 0 에 닿지 않는다

```text
claude   13 → 9 → 9 → 9 → 8      기울기 −1.25, 5라운드에도 8건
codex     4 → 4 → 4 → 3 → 3      기울기 −0.25, 다만 루프가 0 에서 일찍 끝난다
```

### 이 특성들에서 생성된 처방

`bench prescribe` 는 측정된 특성을 하네스 설정으로 옮긴다. 대괄호 안은 근거의 강도이며,
`***` 는 두 모델 이상에서 재현된 것, `**` 는 한 번 측정된 것, `*` 는 판단이다.

```text
claude   [**]  round_cap      라운드 상한을 걸어라 — churn 이 수렴하지 않는다
         [**]  churn_gate     churn 수렴을 정지 기준으로 쓰지 마라
         [***] loop_budget    루프를 짧게 끊어라 — 이 모델은 라운드마다 코드를 불린다

codex    [*]   churn_gate     churn 정지 기준의 근거가 없다 — 라운드로 상한을 걸어라
         [***] loop_budget    루프를 더 돌려도 된다 — 이 모델은 코드를 불리지 않는다
         [*]   comparability  직접 비교 불가 — 도구를 끌 수 없다
```

## 3. 이 벤치가 재지 않는 것

`finds_per_call`(콜당 찾아낸 진짜 결함 수)과 `verbosity_shift`(리포 접근을 열었을 때 지적 수의
변화)는 **tier-2 특성**이다. tier-2 는 실제 코드베이스를 대상으로 사람이 결함의 진위를 판정하는
조건을 말한다.

전자는 판정된 결함 집합이 있어야 계산되는데 tier-1 의 `v0` 는 검증된 정답이라 판정할 결함이
없고, 후자는 리포 접근 유무의 대비가 필요한데 tier-1 과제는 단일 파일이라 대비할 것이 없다.

따라서 이 벤치가 파생된 더 넓은 연구의 가장 강한 결과 — *리뷰어에게 리포 접근을 주면 오탐이
사라진다* — 는 **tier-1 실행으로는 재확인되지 않는다.**
[`../LIMITS.ko.md`](../LIMITS.ko.md) 를 함께 보라.

## 4. 과제 추가

```text
tasks/<slug>/SPEC.md              사람이 읽는 계약
tasks/<slug>/test_acceptance.py   동결 스위트 — 이것이 오라클이다
tasks/<slug>/reference.py         (선택) 알려진 정답 구현
```

그다음 `Task(slug, module_name, n_ac, has_reference)` 로 등록한다. 그 과제에서 나온 수치를
인용하려면 먼저 `oracle.verify()` 를 통과해야 한다.
