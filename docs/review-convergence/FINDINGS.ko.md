# 주요 발견

[English](FINDINGS.md) · 장문 서사: [`STUDY-ko.md`](STUDY-ko.md)

이 문서는 이 벤치마크의 기반이 된 연구와 벤치마크 자체에서 측정한 결과를 정리한 것이다.

```text
tier-1   계약과 고정 테스트가 판정 기준. 사람의 주관적 판정 없이 재현 가능
tier-2   실제 펌웨어 모듈. 결함의 진위는 저자가 판정한 사례연구
```

결과의 한계는 [`../LIMITS.ko.md`](../LIMITS.ko.md)와 함께 봐야 한다.
여기서 **여러 모델이나 조건에서 재현된 문장은 셋뿐**이고, 나머지는 한 번 관측된 결과다.

## 읽기 전에 — 반복해서 나오는 용어

| 용어 | 뜻 |
|---|---|
| **지적**(finding) | 리뷰어가 한 건으로 보고한 항목. 진위 판정과는 별개다 |
| **원시 지적** | 보고된 지적의 총 개수. 같은 문제를 여러 리뷰어가 말하면 그만큼 중복 포함 |
| **고유 지적** | 같은 결함을 가리키는 지적을 하나로 묶은 뒤의 개수. 사람이 읽어야 할 *종류*의 수 |
| **중복** | 원시 ÷ 고유. 3.6× 면 같은 것을 평균 3.6번 반복해 들었다는 뜻 |
| **오탐**(false positive) | 결함이라고 보고됐지만 실제로는 결함이 아닌 것 |
| **bare 프롬프트** | "이 코드를 리뷰해라"에 가까운 최소 지시 |
| **structured 프롬프트** | 무엇을 어떤 순서로 볼지와 출력 형식까지 규정한 지시 |
| **파일만** | 리뷰어에게 대상 파일 하나만 주고 리포지토리는 파일시스템에서 제거한 조건 |
| **리포 접근** | 같은 리뷰어에게 소스 트리를 읽기 전용으로 열어준 조건. **리포 A / B** 는 서로 다른 회사의 두 모델 |
| **혼합** | 한 모델을 반복하는 대신 두 모델에 호출을 나눠 준 조건 |
| **중앙값** | 값을 크기순으로 늘어놓았을 때 한가운데 값. 한 번의 이상치에 흔들리지 않는다 |
| **churn** | 한 라운드에서 추가·삭제된 줄 수. *얼마나 손댔는가*이지 품질이 아니다 |
| **거절률** | 수정자에게 넘긴 지적 중, 수정자가 근거를 밝히고 **고치지 않기로 한** 비율 |
| **인수 조건 / 인수 테스트** | 명세가 보장하는 동작을 검증 가능한 문장으로 쪼갠 것과, 그것을 검사하는 테스트 |

---

## 1. 리뷰 반복과 수정 루프는 서로 다른 활동이다

**가장 강한 결과다.** 서로 다른 세 조건에서 같은 방향이 나왔다.

| | 이득 | 비용 |
|---|---|---|
| **리뷰만 반복** | 진짜 결함 커버리지 34% → 61% → 76% | 없음. 코드가 바뀌지 않는다 |
| **리뷰→수정 루프 반복** | 이미 만점이던 계약 준수율은 40라운드 동안 그대로 | 코드 +24~152%, 한 조건에서 테스트 파손 |

결함을 더 찾는 효과는 리뷰 반복에서 나왔고, 코드 변경의 위험은 수정 쪽에서 생겼다.
둘을 하나의 auto-fix 루프로 묶는 것이 반드시 유리하다는 근거는 없었다.

> **리뷰는 여러 번, 수정은 한 번.**

## 2. 리뷰 1회는 진짜 결함의 약 3분의 1만 찾았다

tier-2. 359줄짜리 펌웨어 모듈을 코드 고정 상태로 10회 독립 리뷰했다.

```text
회차별 지적:   6  6  5  7  5  7  9  5  4  7     범위 4~9, 최대 2.25배 차이
61건  →  고유 결함 14개
```

같은 결함을 서로 다른 문장으로 지적한 항목끼리 묶는 과정도 검증했다.
입력 순서를 바꿔 세 번 반복했을 때 같은 그룹이 나왔고(**ARI 1.000**),
다른 회사 모델로 다시 묶어도 같은 14개가 나왔다.
ARI는 두 클러스터링 결과의 일치도를 나타내며 1.0이면 완전히 같다는 뜻이다.

```text
                 14개 전체        판정된 진짜 10개만
리뷰 1회             44%                34%
     3회             71%                61%
     5회             83%                76%
```

일부 결함은 10회 중 단 한 번만 발견됐다.

## 3. 한 파일만 보여주면 자주 나온 지적이 오히려 더 의심스러웠다

고유 결함 14개 중 **4개는 오탐**이었고, 이 네 개가 가장 자주 보고된 축에 속했다.

```text
오탐의 평균 발견 빈도    6.8 / 10     (8, 7, 7, 5)
진짜의 평균 발견 빈도    3.4 / 10     (9, 7, 6, 3, 3, 2, 1, 1, 1, 1)
```

오탐 네 건은 모두 **파일 밖의 정보가 있어야 판단할 수 있는 문제**였다.
실제 호출 순서, 초기화 경로, 어느 스레드가 함수를 실행하는지 등을 리뷰어는 확인할 수 없었다.

> 여러 리뷰어가 같은 지적에 동의한 이유가 그 지적이 참이어서가 아니라,
> **모두가 같은 정보를 보지 못했기 때문**일 수 있다.

따라서 diff만 주고 여러 리뷰어가 동의한 항목을 자동 채택하는 방식은,
이 데이터에서는 오히려 오탐을 우선 선택했다.

## 4. 소스 트리를 읽게 하자 같은 오탐이 두 모델 모두에서 사라졌다

프롬프트의 한 문단만 바꿨다.

```text
파일 조건:  다른 파일이나 리포지토리를 볼 수 없다
리포 조건:  소스 트리를 read-only로 보고, 결함을 주장하기 전에 호출자와 헤더를 확인한다
```

| | 지적 | 고유 | 진짜 | 오탐 | 정밀도 |
|---|---|---|---|---|---|
| 파일만 | 61 | 14 | 10 | **4** | 71% |
| 리포 접근 (모델 A) | 30 | 7 | 7 | **0** | **100%** |
| 리포 접근 (모델 B) | 37 | — | — | **0** | — |

세 조건의 지적을 함께 묶었을 때도 **ARI 0.978**이었다.
**두 모델 모두 파일 조건에서 나온 같은 오탐 4개를 전부 버렸다.**
이 연구에서 가장 강한 교차 모델 결과다.

두 모델이 보인 반응은 달랐다.

```text
모델 A   61 → 30 지적  (−51%)   전체 지적을 줄였다
모델 B   27 → 37 지적  (+37%)   오히려 지적이 늘었다
```

찾아낸 진짜 결함도 달랐다. 판정된 진짜 10개 중 각각 4개를 찾았지만 **합집합은 5개**였다.
한 결함은 모델 A가 10회 중 1회, 모델 B는 **10회 모두** 찾았다.

### 대가는 재현율이었다

```text
             정밀도       재현율
파일만          71%          77%
리포 접근      100%          54%
```

정밀도는 *보고한 것 중 얼마나 진짜였는가*, 재현율은 *실제 결함 중 얼마나 찾았는가*다.
리포 접근은 오탐을 없앴지만 희미한 진짜 결함도 일부 놓쳤다.
두 조건을 모두 실행해 합치면 20콜에서 13/13을 회복했다.

## 5. 강하게 재현된 것처럼 보였던 회귀는 실험 조건의 산물이었다

파일만 보여준 수정 루프에서 **네 번의 독립 실행이 정확히 같은 네 테스트를 깨뜨렸다.**
하지만 원인이 된 지적은 나중에 오탐으로 판정됐고,
리포 접근을 허용하자 완전히 사라졌으며 리포 접근 루프에서도 재현되지 않았다.

```text
                          파일만        리포 접근
완료 라운드                 15             10
RED 라운드               12 / 15        6 / 10
문제의 네 테스트          매번 실패        한 번도 없음
```

모델이 추가한 방어 코드는 파일만 보면 타당했지만 실제 프로덕션에서는 그 상태에 도달할 수 없었다.
테스트가 **실제 시스템에서는 들어갈 수 없는 상태**를 고정하고 있었던 것이다.

> 같은 테스트가 반복해서 깨진다면 모델이 회귀를 만들었다고 결론짓기 전에,
> **그 테스트가 실제 도달 가능한 상태를 검사하는지** 먼저 확인해야 한다.

## 6. 계약을 모두 만족하는 코드에도 리뷰어는 계속 지적을 낸다

tier-1. 19개 인수 조건에서 만든 23개 테스트를 모두 통과하는 Python 모듈이다.

```text
모델 A, bare 프롬프트          5, 5, 6, 8, 7, 8, 6            중앙값  6
모델 A, structured 프롬프트   11, 11, 12, 11, 12, 12, 11      중앙값 12
모델 B, bare 프롬프트          1, 1, 1, 1, 0, 1, 1            중앙값  1
모델 B, structured 프롬프트    1, 1, 2, 2, 3, 4, 5            중앙값  2
```

15회 중 14회에서 지적이 나왔다.
**40번의 수정 라운드에서 189건을 반영했지만 계약 준수는 한 번도 깨지지 않았다.**
벤치마크 자체 실행에서도 54라운드 모두 23/23이었다.

따라서 이 실험에서 **계약 준수율만으로는 어떤 방식이 더 나은지 구분할 수 없었다.**

## 7. 리뷰어의 침묵은 "다 봤다"는 뜻이 아니다

```text
모델 B, bare         1 → 1 → 0 → 0 → 0     3라운드부터 지적 없음
모델 B, structured   6 → 3 → 2 → 1 → 1     빠르게 감소
모델 A, bare         5 → 6 → 7 → 6 → 7     감소하지 않음
모델 A, structured  12 → 11 → 10 → 11 → 9  감소하지 않음
```

3라운드부터 침묵한 조건은 5라운드 전체에서 **2건**만 찾았다.
같은 코드에 structured 프롬프트를 사용한 조건은 이후에도 시계 실패, 프로세스 제어 예외,
wedge 같은 다른 실패 모드를 계속 찾았다.

> 지적이 0이 됐다고 해서 리뷰가 완료됐다고 볼 수는 없다.

## 8. 계약은 모델이 바꿀 수 있는 영역을 실제로 제한했다

코드의 조건이나 연산을 하나씩 일부러 바꾼 뒤 고정 테스트를 실행했다.
**변경을 넣었을 때 테스트가 실패하면, 그 동작은 계약이 이미 규정한 것으로 보았다.**
이것이 여기서 사용한 뮤테이션 테스트의 기준이다.

```text
뮤테이션 지점 120개
  104  테스트가 잡음 → 계약이 고정한 영역 (87%)
   16  테스트 통과
         9  관측상 같은 동작이라 실제 차이가 없음
         4  테스트 스위트의 빈틈
         3  계약이 실제로 정하지 않은 자유 영역 1개
```

47번의 리뷰-수정 라운드 동안 실제 관측 동작이 바뀐 곳은 **정확히 한 곳**이었고,
바로 계약이 정하지 않은 자유 영역이었다.

즉 **모델이 움직인 자리와 계약이 비워둔 자리가 일치했다.**

한 조건에서는 3라운드와 4라운드가 같은 설계 결정을 반대 방향으로 뒤집었지만
두 설명 모두 논리적이었고 계약도 만족했다.
이 경우 문제는 코드보다 **명세가 그 동작을 정의하지 않았다는 데** 있다.

## 9. 계약이 덜 촘촘하다고 해서 반드시 진동하는 것은 아니다

두 번째 과제에서는 같은 수준의 기능을 19개가 아니라 **8개의 인수 조건**만으로 정의했다.

```text
독립 구현 4개 (모델 A 3개, 모델 B 1개)
  전부 8/8 통과
  6개 구현 쌍 모두 차등 테스트 0/400 → 관측 동작 동일
  크기 54 / 101 / 133 / 138줄 → 최대 2.5배 차이지만 동작은 같음

10라운드 동안 지적 104건을 반영해도 차등 테스트 0/400
```

차등 테스트는 두 판본에 같은 입력 400개를 그대로 재생해 결과가 갈리는지 보는 방법이다.
이 하네스가 실제 차이를 잡는지도 일부러 다른 동작을 심어 검증했고,
95/400, 400/400, 369/400의 차이를 모두 잡았다.

```text
관례가 강함   TTL 경계 · LRU 갱신 · len의 의미     → 4개 구현이 모두 일치
관례가 약함   잘못된 타입을 어떻게 처리할지         → 4개 구현이 3가지 답으로 갈림
```

> 계약이 성기다는 사실 자체가 드리프트를 만드는 것은 아니다.
> **공유된 관례가 없는 곳에서 선택이 갈렸다.**

## 10. 리뷰를 카테고리별로 나누면 반복보다 나은 경우가 있었다

동일한 호출 예산을 사용한 tier-1 결과다.

| 조건 | 콜 | 고유 지적 | 원시 지적 | 중복 |
|---|---|---|---|---|
| 단일 structured | 1 | 11.0 | 11.6 | 1.0× |
| 동일 프롬프트 6콜 | 6 | 19.7 | 69.3 | 3.6× |
| **카테고리 6종** | 6 | **30.0** | **54.7** | 1.8× |

카테고리별로 나누자 **고유 지적은 52% 늘었고, 원시 지적은 21% 줄었다.**
추가 이득은 주로 robustness, naming, style에서 나왔다.

39건을 따로 판정한 결과(팬아웃에서만 나온 것과 두 조건에 공통인 것을 섞어 라벨 없이 판정했다):

```text
REAL 12 (31%)   STYLE 27 (69%)   WRONG 0
```

사실관계가 틀린 지적은 없었지만 대부분은 실제 결함보다 이름, 주석, 구조에 관한 개선 제안이었다.

하지만 **다른 과제에서는 재현되지 않았다.**
펌웨어 과제에서는 같은 예산의 fan-out 재현율이 43%로 단일 리뷰의 50%보다 낮았다.
리뷰 카테고리가 서로 많이 겹쳤기 때문이다.
또 "모듈 내부 상태만 보라"는 좁은 렌즈는 리포 접근으로 사라졌던 오탐 하나를 다시 만들었다.

> fan-out은 리뷰 축이 실제로 분리되는 과제에서만 이득이 있었다.

## 11. 수정 후 재리뷰의 필요성은 라운드보다 변경량(churn)에 가까웠다

리뷰 1회가 모든 문제를 찾지 못하므로, **코드를 전혀 바꾸지 않아도** 두 번째 리뷰에서는 새 지적이 나온다.
그래서 먼저 코드가 그대로일 때 새 지적이 얼마나 나오는지 계산했다. 이것이 귀무분포다.

기존 독립 리뷰 9회에서 서로 겹치지 않는 세 묶음의 조합 1680개를 모두 계산했다.

```text
코드 무변경       신규 지적률 중앙값 11%, 범위 0~31%
실제로 수정한 뒤   신규 지적률 77% / 89% / 63%
```

수정 뒤의 신규율은 코드가 그대로일 때의 범위를 크게 벗어났다.
동시에 처음 전달한 지적의 **74~80%는 다음 리뷰에서 사라졌다.**

신규 지적률과 가장 함께 움직인 것은 수정량이었다.

```text
수정 churn (줄)     143   87   82   36   28   36
진짜 신규율          82%   62%   43%  50%  40%  20%      r = 0.837 (n=6)
```

> 재리뷰의 질문은 "몇 라운드째인가?"보다 **"방금 코드를 얼마나 새로 썼는가?"**에 가깝다.
> 파일 절반을 다시 썼다면 사실상 새 코드에 대한 첫 리뷰다.

## 12. 준수율은 같았지만 코드 크기와 복잡도는 달랐다

10개 조건, 47라운드가 모두 19/19로 계약을 만족했다.
하지만 같은 코드들의 유지보수성 지표는 크게 달랐다.

```text
Cognitive Complexity   structured −17%   ·   bare +26%   ·   계약 없음 +58%
가장 복잡한 함수          6.3              ·      10.3      ·      15
```

Cognitive Complexity는 코드를 읽을 때 머리에 쌓아야 하는 중첩과 분기의 양을 재는 지표다.

프롬프트와 계약의 효과는 단순 합보다 컸다.

```text
기준: bare + 계약 없음      37.0
계약만 추가             →   33.3   (−3.7)
structured만 적용       →   32.3   (−4.7)
둘 다 적용              →   24.0  (−13.0)
```

각 효과를 따로 더하면 8.4인데 둘을 함께 적용했을 때는 13.0이 줄었다.
즉 두 조건 사이에 **상호작용**이 있었다.

한편 churn은 **품질 점수보다는 변경 비용을 나타내는 지표**에 가까웠다.
가장 많은 줄을 바꾼 조건이 최종적으로 가장 작고 단순한 코드를 만들기도 했다.

## 13. 실험에서 "계약"이라 부른 것은 사실 두 가지였다

처음에는 계약이라는 변수 안에 두 요소가 같이 들어 있었다.

```text
B  공개 API와 동작 범위는 고정이며, 범위 밖 변경은 거절하라
C  실제 명세(SPEC) 문서
```

이를 분리해 측정했다.

| 수정자에게 준 정보 | 거절률 | 최종 LOC | 누적 churn |
|---|---|---|---|
| A — 요청받지 않은 부분은 건드리지 마라 | 26% | 254 | 195 |
| A+B — 공개 표면도 고정이다 | **50%** | 237 | **136** |
| A+B+C — 실제 명세까지 제공 | 26% | **202** | 191 |

공개 표면이 고정이라고만 알려주면 코드 크기와 churn은 줄었지만,
대조할 명세가 없기 때문에 수정자는 애매한 제안을 많이 거절했다.
거절의 근거도 달랐다 — 명세가 없을 때는 거절 17건 중 인수 조건을 인용한 것이 0건이었고
(대신 코드 자신의 docstring을 인용했다), 명세가 있을 때는 12건 중 7건이 조건을 인용했다.

> **범위를 고정하는 문장은 코드 팽창을 억제했고,
> 실제 명세는 무엇을 받아들이고 거절할지 판단하는 기준을 제공했다.**
> 명세 없이 그 한 줄만으로 LOC −7%, churn −30% 였고, 명세는 그 위에 판단의 정확성을 더했다.

## 14. 테스트는 읽히되 수정하지 못하게 하자 빌드 실패가 사라졌다

리뷰어와 수정자는 전체 소스 트리를 볼 수 있었지만 테스트 하네스는 특정 모듈 하나만 연결했다.
이 상태에서 모델이 **타당한 모듈 간 수정**을 하자 테스트 빌드가 깨졌다.

코드가 틀린 것도, 테스트 자체가 틀린 것도 아니었다.
**판정 기준인 테스트(오라클)의 범위가 리뷰 범위보다 좁았던 것**이다.

테스트 디렉터리를 read-only로 보여주자 수정자가 이런 변경을 스스로 거절했다.

> *"이 수정은 테스트까지 바꿔야 가능하다."*
> *"테스트가 현재 링 용량을 고정하고 있다."*
> *"이 파일 안에서는 고칠 수 없다. 필요한 정보는 sensor.c에 있다."*

빌드 시스템을 바꾸지 않았는데도 해당 루프의 빌드 실패가 0이 됐다.

다만 거절한 항목의 약 3분의 1은 **"실제로 문제지만 현재 수정 범위 밖"**이었다.
해결한 것이 아니라 보류한 것이다.

## 15. 같은 모델을 반복하기보다 모델을 섞는 편이 효율적이었다

기존 실행에서 가능한 모든 부분집합을 계산했다. 추가 모델 호출은 없었다.
분모는 판정된 진짜 결함 10개이며, 각 값은 **진짜 발견 / 오탐 발견**의 평균이다.

| 콜 | 파일만 | 리포 A | 리포 B | **혼합** |
|---|---|---|---|---|
| 1 | 3.40 / **2.70** | 1.40 / 0 | 2.70 / 0 | 2.70 / 0 |
| 2 | 5.04 / **3.62** | 2.09 / 0 | 3.07 / 0 | **3.18** / 0 |
| 3 | 6.11 / **3.90** | 2.54 / 0 | 3.27 / 0 | **3.57** / 0 |
| 4 | 6.93 / **3.98** | 2.90 / 0 | 3.40 / 0 | **3.90** / 0 |
| 6 | 8.20 / **4.00** | 3.43 / 0 | 3.60 / 0 | **4.43** / 0 |

**혼합 3콜(3.57)이 단일 모델 6콜(리포 A, 3.43)보다 높았다.**
그리고 같은 콜 수끼리 비교하면 2콜 이상 모든 구간에서 혼합이 우세했다.

파일만 보는 리뷰는 콜당 더 많이 찾지만 오탐도 빠르게 늘었다.
다섯 번째 호출이면 판정된 오탐 4개가 모두 등장했다.
즉 절약한 비용은 사라진 것이 아니라 **사람의 선별 비용으로 옮겨간 것**에 가깝다.

*이 표의 분모에는 리포 접근 조건에서만 새로 발견된 결함이 빠져 있어,
리포 접근에 유리하게 만든 계산은 아니다.*

## 16. 벤치마크 자체에서도 모델별 루프 특성이 달랐다

tier-1. `retry_policy` 과제를 두 모델로 각각 세 루프씩 실행한 결과다(2026-08-21).

| 모델 | 콜 | 비용 | loop_decay | churn | 거절률 | 코드 크기 | 도구 차단 |
|---|---|---|---|---|---|---|---|
| A | 30 | $15.74 | −1.25 | 수렴 안 함 (1:2로 갈림) | 0.209 | **1.258×** | 가능 |
| B | 24 | 미상 | −0.25 | 측정 불가 (루프가 일찍 끝남) | 0.273 | **0.906×** | **불가** |

`loop_decay`는 라운드가 갈수록 지적 수가 줄어드는 기울기다. 음수면 줄어든다는 뜻이고,
−1.25는 라운드마다 평균 1.25건씩 줄었다는 뜻이다. `코드 크기`는 마지막 라운드의 코드 줄 수를
시작 코드로 나눈 값이라 1보다 크면 불어난 것, 작으면 줄어든 것이다. `도구 차단`은 그 CLI 에서
모델의 도구 사용을 실제로 끌 수 있는지를 가리킨다 — 끌 수 없는 모델을 같은 표에 놓는 것 자체가
교란이므로 결과에 함께 적는다.

코드 크기의 방향은 모델마다 달랐다.
한 모델은 지적을 반영할수록 코드를 키웠고, 다른 모델은 오히려 줄였다.
리뷰-수정 루프를 얼마나 오래 돌릴 수 있는지도 이런 모델 특성의 영향을 받는다.

**churn 수렴은 안정적인 정지 기준이 되지 못했다.**
모델 A의 세 루프에서 측정된 비율은 0.611 / 0.732 / 0.720으로 임계값 0.7 주변에 걸쳐 있었다.
모델 B는 루프가 너무 일찍 끝나 수렴 여부 자체를 계산할 수 없었다.

> **"측정할 수 없었다"와 "수렴하지 않았다"는 다른 결과다.**
