# 그래서 리뷰를 어떻게 해야 하는가

[English](PRESCRIPTION.md) · 장문 서사: [`STUDY-ko-rewrite.md`](STUDY-ko-rewrite.md)

측정이 뒷받침하는 레시피. 모든 줄에 근거를 병기한다. 숫자는
[`FINDINGS.md`](FINDINGS.md), 이것으로 주장할 수 없는 것은 [`LIMITS.ko.md`](LIMITS.ko.md).

```
***  모델 또는 조건을 넘어 재현됨
**   한 번 측정됨
*    판단
```

---

## 가장 큰 것

| | 이득 | 비용 |
|---|---|---|
| **리뷰만 반복** | 진짜 결함 커버리지 34% → 61% → 76% | 없음. 코드가 안 바뀐다 |
| **리뷰→수정 루프 반복** | 0 | 코드 +24% ~ +152% |

> ### 리뷰는 여러 번, 수정은 한 번. `***`

커버리지 이득은 전부 리뷰 쪽에, 코드 위험은 전부 수정 쪽에 있다. 둘을 번갈아 도는 하네스는
이득 대비 위험을 최대로 만든다.

---

## 절차

```
1  리뷰어에게 소스 트리 읽기 권한을 준다                            ***
     파일만: 오탐 29%.  리포 열림: 0%.  두 모델 모두.
     대가는 재현율 77% → 54%. 둘 다 원하면 두 조건을 다 돌려 합집합을 취한다
     (20콜에 13/13).

2  콜을 감당할 수 있으면 반복 대신 카테고리로 쪼갠다                  **
     같은 6콜: 동일 프롬프트 → 고유 19.7, 카테고리 6종 → 30.0 (+52%),
     원시 지적은 오히려 21% 적다.
     ⚠ 렌즈가 겹치는 과제에서는 이득이 없었다. 축이 실제로 분리되는지 먼저 확인하라.
     ⚠ 좁은 렌즈는 1번을 부분적으로 되돌린다 — "모듈 내부 상태만 보라"는 배정이
       리포 접근으로 없앤 오탐을 하나 되살렸다.

3  합의 횟수를 진위의 대리변수로 쓰지 않는다                         ***
     파일-스코프에서 오탐의 평균 발견빈도 10회 중 6.8, 진짜 3.4 — 반-예측적이다.
     리포를 열면 그 상관이 뒤집힌다.
     ⚠ 한 경우에 2번과 충돌한다. 그 조합의 필터 규칙은 아직 없다.

4  사람이 훑는다                                                 ** — 자동화하지 않는다
     지적의 69% 는 이름·주석·구조다. 그건 수정자에게 보내지 않는다.
     이 단계를 빼도 동작은 했으나(수정자가 34% 를 대신 거절) 코드가 3라운드에 152% 불었다.

5  한 번에 고친다. 계약과 테스트 읽기 권한을 함께 준다                **
     넘긴 지적의 74~80% 가 실제로 사라진다.
     편집 없는 읽기 권한은 수정자가 모듈 밖 수정을 시도하는 대신 거절하게 만든다 —
     빌드 시스템을 건드리지 않고 루프 전체의 빌드 실패가 0 이 됐다.
     고치는 게 아니라 미루는 것이고, 그것이 이 거래의 내용이다.

6  테스트와 크기와 복잡도와 churn 을 같이 찍는다                     ***
     준수율은 10개 팔 47라운드 전부 19/19 였고, 이 벤치 자신의 실행에서도 54라운드 전부
     23/23 이었다. 아무것도 판별하지 못한다.
     갈라지는 곳: 복잡도 −17%(structured) vs +58%(계약 없음).
     비용은 AST 한 번. 모델 호출 0.

7  재리뷰 여부를 라운드 수가 아니라 churn 으로 정한다                 **
     작게 고쳤으면 수확도 작다, 넘어가라. 크게 고쳤으면 그건 새 코드의 첫 리뷰다.
     신규 지적률이 수정 churn 을 r = 0.837 로 따라간다.
     ⚠ "churn 이 수렴하면 멈춘다" 는 조건부다. 계약이 있는 과제에서는 성립했고 없는
       과제에서는 실패했다 — churn 이 194 → 262 → 395 로 늘었고 루프는 이 규칙이
       기각하는 기준인 "지적 0" 으로 끝났다. 계약이 없으면 라운드로 상한을 걸어라.

8  루프가 같은 결정을 두 번 뒤집으면 스펙을 고쳐라                    **
     47라운드에서 움직인 관측 동작은 정확히 하나였고, 계약이 정의하지 않은 유일한 영역이었다.
     진동은 자유-스펙 신호이며, 공짜로 얻는 스펙 감사다.

9  스펙이 없어도 "공개 표면은 고정" 한 줄은 준다                      **
     한 줄로 LOC −7%, churn −30%.
     ⚠ 거절률이 26% → 50% 로 두 배가 된다. 확인할 문서 없이 "고정" 만 들으면 애매한 것을
       전부 거절한다. 그 절반이 진짜 손실인지는 측정하지 않았다.

10 한 모델을 두 번 돌리는 대신 두 모델을 한 번씩 돌린다               ***
     둘 다 같은 오탐 4건을 버렸지만 찾아낸 진짜는 달랐다(각 4/10, 합집합 5/10).
     혼합 3콜이 단일 6콜을 이긴다.
```

## 예산

기존 실행의 모든 부분집합에 대한 전수 계산. 판정된 결함 10개 기준 (진짜 발견 / 오탐 발견):

| 콜 | 파일만 | 리포 A | 리포 B | **혼합** |
|---|---|---|---|---|
| 2 | 5.04 / **3.62** | 2.09 / 0 | 3.07 / 0 | **3.18** / 0 |
| 3 | 6.11 / **3.90** | 2.54 / 0 | 3.27 / 0 | **3.57** / 0 |
| 4 | 6.93 / **3.98** | 2.90 / 0 | 3.40 / 0 | **3.90** / 0 |
| 6 | 8.20 / **4.00** | 3.43 / 0 | 3.60 / 0 | **4.43** / 0 |

**2콜:** 모델별 하나씩. 진짜 3.18, 오탐 0. 같은 2콜을 한 모델에 파일-only 로 쓰면 진짜
5.04 를 보지만, 오탐 3.62 를 사람에게 넘긴다 — 그리고 그것들이 그 집합에서 가장 그럴듯해
보이는 지적들이다.

**4콜:** 모델별 둘씩. 3.90 — 단일 모델 10콜(4.00)에 근접하면서 예산은 60% 적다.

파일만은 콜당 더 많이 찾는다. 그 예산은 절약된 것이 아니라 **선별하는 사람에게 옮겨진 것**이다.

## 무한 루프를 벗어나는 법

정지 기준 후보 넷 중 셋이 살아남지 못한다.

```
churn → 0        계약이 있는 과제에서만 성립. 그 밖에서는 churn 이 단조 증가했다
지적 0           실제로 한 루프를 끝낸 것 — 그리고 7번 규칙이 기각하는 기준이다
라운드 상한       수렴이 아니라 절단이다
루프를 안 돈다    ← 남는 것
```

조용한 두 번째 정지 요인이 있다. **파일이 커지면 리뷰가 느려진다.** 한 루프에서 900줄짜리
파일에 대한 4라운드 리뷰가 15분 상한을 넘겼다. 충분히 오래 돌리면 루프는 수렴이 아니라
타임아웃으로 끝난다.

## 스펙을 만드는 팀이라면

위 여섯은 그대로 적용된다. 둘은 당신만 할 수 있다.

**준수율 옆에 크기·복잡도·churn 을 같이 찍어라.** AST 한 번, 모델 호출 0. 그 둘이 갈라지는
순간이 루프가 코드를 나쁘게 만들기 시작한 순간이다.

**진동을 스펙 감사로 취급하라.** 루프가 자기를 뒤집는 자리가 곧 당신의 계약이 침묵하는
자리이고, 그것을 모으는 데는 비용이 들지 않는다.

### 카나리의 1분짜리 팀 버전

연구용 장치는 필요 없다.

> 월 1회, 리뷰어에게 리뷰 대상 파일이 아니라 **그 호출자 파일의 N행**을 인용하게 하라.
> 못 하면 접근 권한이 애초에 붙지 않은 것이다.

*"설정이 적용되지 않았다"* 와 *"모델이 원래 그렇다"* 는 밖에서 보면 똑같이 생겼다.
그 확인 하나가 둘을 가른다.
